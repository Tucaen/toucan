# Project agent memory

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

- ADE hosts FirstMate only through Windows' WSL host; `createUnsupportedFirstMateRuntime` in `src/main/firstmate-runtime.ts` refuses every other platform, so there is no second host implementation to extend. ADE hosts the FirstMate captain as an ACP conversation, not a tmux pane. `src/renderer/src/firstmate-project-catalog.ts` gives it the machine-readable ADE project catalog and a hint-only active project; FirstMate resolves each task and pins the selected project/provider carrier from `src/shared/firstmate-task-context.ts` at dispatch. Before calling `fm-spawn.sh`, the dispatch contract requires the captain to validate the pinned context through the managed ADE spawn gate (`$FM_HOME/bin/ade-spawn-gate`); `src/main/firstmate-spawn-gate.ts` owns the pure validation function that checks the context against ADE's authoritative project record and current validator, and the WSL gate script in `src/main/firstmate-runtime.ts` mirrors that logic for the captain to call. The existing lifecycle validation in `taskContextProblem` remains as a corruption/backstop check. Lifecycle, app-native wake, concurrent task-scoped validation, and provider/model wrappers are owned by `src/main/firstmate-lifecycle.ts`, `src/main/firstmate-lifecycle-coordinator.ts`, and `src/main/firstmate-runtime.ts`. Each validation dispatch gets its own no-mistakes home under `state/validators/{scope-hash}/no-mistakes/` so differently-pinned tasks validate concurrently without clobbering each other's pipeline configuration. Before supervising a reported crew worktree, ADE proves read-only that it belongs to the pinned checkout and is not the primary tree: the runtime gathers `git rev-parse` common/dir facts in WSL and `src/main/firstmate-worktree-provenance.ts` owns the verdict; ADE never allocates a worktree of its own. The integration contracts have one home each: `src/shared/firstmate-runtime-record.ts` owns the `ade-runtime.json` record (type, serializer, parser); `src/main/firstmate-environment.ts` owns the ADE/FirstMate variable names and process/tmux env construction; `src/main/firstmate-paths.ts` owns canonical Windows paths and Windows-to-WSL conversion (the renderer consumes registered paths, never deriving them); `errorMessage` in `src/shared/text.ts` owns unknown-error-to-message conversion. Inline WSL programs receive a serialized record or generic key/value args and never restate the schema.
- Sidebar projects are durable external FirstMate projects, never clones under FirstMate's managed `projects` directory. `src/main/firstmate-external-projects.ts` owns identity, canonical paths, posture defaults, collisions, and migration, and `src/main/firstmate-project-origin.ts` owns which origins are accepted. Registration writes only ADE's own file in the private home: `data/projects.md` is firstmate-private and rebuilt from the clones under `projects/`, so ADE reads it and lets an entry recorded there for a checkout outrank ADE's own record. Its format and posture vocabulary belong to the managed distro's `bin/fm-project-mode.sh`. Registration only reads a checkout; anything that would write inside one needs a separate explicit authorization.
- `.firstmate-panel` and `.terminal-node` (canvas chat nodes) are both `overflow: hidden`, so any dropdown/menu anchored inside them with CSS `position: absolute` clips at that ancestor's edge. `SelectorPicker` in `src/renderer/src/ChatNode.tsx` (the Provider/Model/Permissions pickers) instead portals its menu to `document.body` and positions it in JS against the trigger button's viewport rect via `computeNodePickerMenuPosition` in `src/renderer/src/node-picker-menu-position.ts`, clamped to stay fully on-screen. Follow the same portal pattern for any new floating menu inside these containers rather than CSS anchoring.
- The WSL shell scripts in `src/main/firstmate-runtime.ts` are JS template literals that get written through nested *unquoted* heredocs (`<<EOF`, needed so the outer script's variables like `$base`/`$HOME` expand into the generated file). A single backslash before `$` (e.g. `"\$@"`) is not a recognized JS escape, so the JS parser silently drops it before the string ever reaches the shell — the heredoc then sees a bare `$@`/`$name` and expands it immediately against the *outer* script's own (usually empty) context instead of deferring it into the written file. To defer a variable through such a heredoc, write a double backslash in the JS source (`"\\$@"`) so exactly one literal backslash survives into the shell text. `home/bin/claude`/`home/bin/codex` health is verified by content (`WSL_INSPECT_SCRIPT` greps for the literal forwarded-argument invocation, not just `-x`), because a wrapper can be present and executable yet still broken this way.
- Every ACP agent session (not just FirstMate's) gets a `CaptainWakeGate` (generic over payload type, `src/main/firstmate-captain-wake.ts`, created in `src/main/acp-session-manager.ts`'s `create()`), so `promptWhenIdle(id, content)` queues-and-delivers-on-idle for any session id, where `content` is either plain text or the `AgentPromptBlock[]` array (`src/shared/agent.ts`) a pasted-image attachment adds alongside it. The composer (`Composer` in `src/renderer/src/ChatNode.tsx`, hook logic in `src/renderer/src/use-agent-conversation.ts`) submits through it — `window.agentApi.promptWhenIdle` (IPC `agent:prompt-when-idle`) — whenever `status === 'working'`, so typing while the agent is busy queues rather than blocking; the gate is a real FIFO, so every enqueued message is eventually delivered in submission order, none superseded or dropped (see `firstmate-captain-wake.test.ts`). Whether a session accepts an `image` block at all is a per-agent handshake fact, not a given: `RunningAgent.imageSupport` in `acp-session-manager.ts` is set from `initialize`'s `agentCapabilities.promptCapabilities.image` (Claude and Codex may differ), and `imageCapabilityGuard` rejects an image block for a session that never advertised support rather than forwarding it and letting the agent mishandle it.
- Account-wide hourly (`five_hour`)/weekly (`seven_day`) usage-limit status comes from the `quota-axi --provider <p> --json` CLI, which always exits 0 and reports an empty `windows` array for an unauthenticated/unreachable provider rather than erroring — `FirstMateRuntime.quotaStatus(provider)` in `src/main/firstmate-runtime.ts` wraps that call through the same WSL `run()` helper as other actions, with a short in-memory cache/in-flight-coalescing per provider so multiple open panels/nodes polling on their own timers don't each trigger a `quota-axi` invocation. Like every other managed-environment invocation of `claude`/`codex` in this file (see the wrapper-script generation's `export CLAUDE_CONFIG_DIR=`/`export CODEX_HOME=`), `quotaStatus` must set the matching managed config-dir env var (`CLAUDE_CONFIG_DIR=${readyPaths.homePath}/claude` or `CODEX_HOME=${readyPaths.homePath}/codex`) on the `quota-axi` invocation itself — otherwise `quota-axi` falls back to its own default credential discovery instead of checking the same managed identity ADE's real conversations use, and the Limits display looks permanently unavailable regardless of auth state. The renderer side is `src/renderer/src/use-firstmate-quota.ts` (the poll hook) and `src/renderer/src/AgentUsageStatus.tsx` (`UsageStat`/`QuotaStat`, shared by both `FirstMatePanel.tsx`'s settings bar and `ChatNode.tsx`'s header); live per-conversation context-window usage is a separate signal carried by the ACP `usage_update` event, surfaced as `AgentUsage` in `src/renderer/src/use-agent-conversation.ts`.
- There are two test runners: `tests/**/*.test.ts` (compiled by `tsc -p tsconfig.test.json`, run with `node --test`) covers non-UI logic and has no DOM; `tests/**/*.dom.test.tsx` (Vitest + jsdom + `@testing-library/react`, config in `vitest.config.ts`, setup in `tests/dom/setup.ts`) actually renders renderer components/hooks instead of regex-matching their source text. `npm test` runs both; `npm run test:dom` runs just the Vitest side. Mock the preload bridge with `tests/dom/agent-api-mock.ts` (`createMockAgentApi`) and `window.firstMateApi = {...} as unknown as FirstMateApi` to drive `use-agent-conversation.ts`/`use-firstmate-quota.ts` hooks via `renderHook`. `FirstMatePanel.tsx` and the default `ChatNode.tsx` export pull in `@xyflow/react`'s `NodeResizer` and the `@moonshine-ai/moonshine-wasm` voice prototype, both of which need more than jsdom (a `ReactFlowProvider`, a real audio stack) to mount — test their prop-driven pieces instead (`ChatView`/`SelectorPicker`/`Composer` from `ChatNode.tsx`, `UsageStat`/`QuotaStat` from `AgentUsageStatus.tsx`) and leave cross-process IPC wiring (preload/main/`acp-session-manager.ts`) as documented source-text assertions in the sibling `.test.ts` file.
- ACP auth-required detection has one home, `isAuthRequired` in `src/main/acp-session-manager.ts`, feeding both `promptFailure` (mid-conversation) and `openSession`'s catch (session creation/resume) so every auth failure reaches the same `{ type: 'auth', methods }` sign-in UI. Not every agent auth failure carries the ACP protocol's `-32000 authRequired` code: reproduced empirically by driving `claude-agent-acp` directly over stdio with a scratch, corrupted `CLAUDE_CONFIG_DIR/.credentials.json` (never the shared managed one), an expired/unrefreshable Claude OAuth session surfaces as a generic `-32603` internal error whose `data.errorKind` is the SDK's own `"authentication_failed"` marker (`SDKAssistantMessageError` in `@anthropic-ai/claude-agent-sdk`'s types; `errorKindData` in the adapter's source documents this as the intended dispatch convention over pattern-matching message text). `isAuthRequired` checks both signals. If a future provider's auth failure still falls through to the dead-end generic-error path, reproduce the same way (direct adapter stdio drive with a scratch broken credential file) to find its actual error shape before guessing at a fix.
  - `RunningAgent.authRequired` (set true wherever `isAuthRequired` routes to `auth_required`, cleared only when a fresh `openSession` succeeds) gates `runPrompt` via the pure, unit-tested `promptGuard` helper. Without it, a wake-gate queue built up while `working` (see the entry below) drains straight through the same broken credential once the active prompt hits `auth_required`, re-sending a fresh `auth`/`auth_required` event pair (and flashing `status: 'working'` in between) once per queued message — the sign-in panel never settles long enough to read or click. See `tests/acp-session-manager-auth.test.ts`'s wake-gate-drain test.
  - The sign-in URL a terminal-auth login subprocess prints (or an `elicitation.create` URL request) is *not* safe to show only via the transient `status.message` → `detail` pipe: `.chat-detail` in `styles.css` is `pointer-events: none` and `white-space: nowrap; overflow: hidden` (an unclickable, truncated, single-line tooltip that the very next status ping overwrites) — that combination is the concrete cause of a sign-in link "flashing by too fast to click." `extractLoginUrl` pulls the URL out of that text and the manager proactively calls `shell.openExternal` on it (covers CLI-internal browser-launch failures, e.g. no configured URL handler in a headless/WSL desktop) *and* emits a dedicated `{ type: 'auth_link', url }` event; `use-agent-conversation.ts` keeps that in its own `authLink` state (cleared only by a fresh `auth` event or a successful reauth, never by an unrelated status message) so `AuthPanel` in `ChatNode.tsx` can render it as a persistent, always-clickable "open sign-in link again" button (wired through `agent:open-auth-link` IPC to `shell.openExternal`, since Electron's default `target="_blank"` handling for an in-DOM anchor is unreliable without a `setWindowOpenHandler`). Also: `AuthPanel` must never render nothing while `status === 'auth_required'`, even if `authMethods` is empty — always show the panel shell so there's at least a visible affordance instead of a silent dead end. The real re-auth link arrives while `status` is transiently `'starting'` (the span of the `authenticate()` call), not `'auth_required'` — `useAgentConversation` tracks this separately as `reauthenticating` (true for the whole `authenticate()` call), and both `AuthPanel`'s render condition in `ChatNode.tsx` and the `authMethods`/`authLink` exposure in `use-agent-conversation.ts` key off `status === 'auth_required' || reauthenticating`, not `status` alone, or the panel and link vanish at the exact moment the link shows up.
- `claude-agent-acp`'s `replaySessionHistory()` (vendored under `node_modules/@agentclientprotocol/claude-agent-acp`) replays a resumed session's raw saved log near-verbatim as `session/update` notifications, applying only two narrow library-side filters (a synthetic-login-message skip, a local-command-metadata strip) — it does not know about FirstMate's own supervision injections (`<task-notification>`/`<system-reminder>`-wrapped Stop-hook/wake text), so those leak into the chat view on resume even though the live prompt loop never shows them. Never hand-patch the vendored package (overwritten on reinstall); `isInternalNotificationText` in `src/main/acp-session-manager.ts` filters these out of `user_message_chunk` content at the single point ADE consumes `session/update` for both live and replayed updates, so the fix covers resume without needing to replicate however the live loop suppresses them. See `tests/acp-session-manager-replay-filter.test.ts` for the real wrapper shape.
- A task's live worker binding travels as one `window=` key (tmux `session:window`, e.g. `firstmate:fm-<task-id>`) in the same per-task `.meta` file `worktree=` already comes from; `firstMateLifecycleFromFiles` in `src/main/firstmate-lifecycle.ts` parses both through the same `attachContext` closure onto `FirstMateLifecycleTask.window`, so anything needing the binding reads it from there rather than re-parsing meta. `FirstMateRuntime.openWorkerTerminal(taskId)` in `src/main/firstmate-runtime.ts` reuses that field plus the generic `openTerminal` helper (previously GitHub-sign-in-only) to attach a real terminal to the task's live tmux window, wired to a "View terminal" button on every lifecycle row in `FirstMatePanel.tsx`. Sharp edge verified empirically: `tmux attach-session -t "session:window"` attaches directly to that specific window already (tmux's target-window parsing degrades a target-session argument that carries a colon), so this never needs the `select-window`-chained-with-`\;` form — which matters because Windows Terminal's own CLI treats bare `;` as its own multi-action separator and would need extra escaping to pass it through to tmux. `openWorkerTerminal` also probes `tmux has-session -t <window>` first so a dead/missing binding reports a clear message instead of opening a broken terminal.
