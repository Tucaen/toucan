# Project agent memory

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

- Every non-interactive `node:child_process` launch must apply `hiddenProcessOptions` from `src/main/background-process.ts`; it applies `windowsHide: true` last so no caller can accidentally re-enable transient Windows command windows. ACP adapters additionally inherit the preload policy in `agent-process.ts`, which covers provider CLIs they spawn themselves. The Codex rate-limit reader must resolve Windows npm shims to the matching native platform executable and launch it directly: hiding an intermediate `codex.js` wrapper does not prevent its inherited-stdio child from briefly surfacing a `PseudoConsoleWindow`. The `node-pty` terminal path is intentionally separate because it owns Toucan's interactive terminal surface. `tests/background-process.test.ts` inventories child-process importers to enforce this boundary, while `tests/codex-rate-limits.test.ts` locks down the native shim resolution. The same shim rule binds test launchers: current Node refuses to spawn a Windows `.cmd` without a shell (EINVAL), so `tests/architecture-dependencies.test.ts` runs dependency-cruiser's own JS entry under `process.execPath` instead of `node_modules/.bin` - and asserts a cruise report was actually produced, because a launcher that never ran otherwise presents itself as every rule being broken at once.
- A git worktree is a first-class workspace entity, not a per-node side effect. It is created explicitly (canvas context menu -> Worktree), persisted in `WorkspaceState.worktrees`, and rendered as its own `worktreeNode`; session nodes _reference_ one via `worktreeId`, so several nodes can share a worktree and closing a node never touches it. `TerminalNodeData.workingDirectory` (resolved in `restoreCanvasWorkspace`/`addSessionNode`) is the only value that may be sent as a `cwd` - `projectPath` is display-only now. A node whose worktree record vanished restores `detachedFromWorktree` and dormant rather than silently falling back to the project checkout. Teardown lives in `src/main/git-worktree.ts` and is evidence-gated: it proves shared git-common-dir and non-primary identity, then reports `WorktreeRemovalBlocker`s for dirty/untracked/stashed/unpublished work; missing evidence produces a blocker, never permission. `isForcibleBlocker` decides what a confirmation may override, and removal never deletes the branch, so forcing can only cost uncommitted and untracked files. `planWorktreeRemoval` in `src/renderer/src/worktree-removal.ts` folds attached-node count into that verdict. See `tests/git-worktree.test.ts` and `tests/worktree-rules.test.ts`.
- Attachment is what makes a node run in a worktree; an association is not attachment. `src/renderer/src/worktree-attachment.ts` owns both halves: `applyAttachedNodeCounts` derives every worktree's count from nodes carrying `worktreeId` (never from `activeWorktreeId`), and `adoptClaimedWorktrees` redeems the weak association discovery leaves behind. A worktree an agent made for itself is matched to its node by the claim `settle-worktree.mjs` writes when it sees `TOUCAN_NODE_ID` - so that variable must reach the adapter process itself via `agentProcessEnvironment` at the `buildAgentProcessLaunch` call, not only the `RunningAgent` record beside it. That claim is written after `git worktree add` and after the project's setup command, routinely later than the sweep that records the worktree, so `matchWorktreeClaims` reports claims for every worktree git lists (not only newly discovered ones) and `applyWorktreeClaims` links them against the whole canvas; a claim is a file agents append to and never prune, so a node is only ever linked or moved within its own project. Redeeming a claim restarts the session in the worktree, so it is Codex-only (Claude transcripts are directory-scoped) and only at a boundary with nothing in flight: `idle`, `result`, `dormant`, `exited` - never `working`, `starting`, `attention`, or `stalled`. `invokesWorktreeSkill` recognises both the unqualified `/implement-in-worktree` and the namespaced `/$<ns>:implement-in-worktree` slash completion actually inserts, matched by shape so no host's branding is baked in; recognising the prompt up front is the normal path - `hoistSlashCommand` (see the composer entry) puts a mid-prompt invocation on the first line, so that path covers those too - and claimed discovery is the fallback for a worktree the agent made anyway. See `tests/worktree-attachment.test.ts`, `tests/worktree-adoption.dom.test.tsx`, `tests/worktree-handoff.test.ts` and `tests/acp-session-manager-launch.test.ts`.
- Terminal identity has two layers: the workspace persists a durable `sessionId`, while `src/main/terminal-manager.ts` exclusively creates and owns the process `incarnationId` and liveness verdict. Every terminal IPC command and event carries both identities; never route by canvas node ID alone or infer exit from renderer/transport loss. Persisted live terminals hydrate as `unverifiable`; only the process owner's exit callback establishes `exited`.
- Plain-terminal history lives separately in `src/main/terminal-scrollback-store.ts`: one exact-incarnation snapshot per durable session, bounded to 512 KiB/seven days and removed with the canvas node. `TerminalNode` may render it while dormant, but it is display-only; never use retained output for liveness, input authorization, prompt detection, or any other operational state.
- The terminal-context edge (terminal node → chat node) is the canvas's only edge kind and grants exactly one capability: the chat node's agent may read that terminal's output (design and slices in `docs/plans/terminal-context-edge.md`; read-only by construction, no generic untyped edges). Edge state is runtime-only React state in `App.tsx` beside `nodes` - never `WorkspaceState`, closing either node drops it via the same removal wrapper that feeds `recentlyClosedNodes` - and every rule (what `isValidConnection` admits, node-close pruning, the mirror shape) is a pure function in `src/renderer/src/terminal-context-edges.ts`. Main is the privilege boundary: the set is mirrored by full-set-replace IPC (idempotent, last-write-wins, self-healing across renderer reloads) into `src/main/terminal-context-registry.ts`, keyed by durable terminal `sessionId` plus agent session id (the chat node's id, what `AgentApi` routes by), and any terminal read must check `hasEdge` there at call time - a tool definition being present in a session never implies the capability. See `tests/terminal-context-edges.test.ts` and `tests/terminal-context-registry.test.ts`.
- What an agent may read through a terminal-context edge is `src/main/terminal-output-tail.ts`, not the scrollback store: the store's file is write-debounced and unfsynced, so a mid-build read there returns the previous build. The manager keeps its own in-memory tail per terminal off the same `onData`, retaining `TERMINAL_SCROLLBACK_MAX_BYTES` (trimmed at twice that, because trimming means measuring the whole buffer on the renderer's hot path), and it outlives the incarnation's exit so a read after a crash returns the crash output. Store raw, strip on serve (`normalizeTerminalOutput` lives in `src/shared/terminal-output.ts` for this) - byte offsets must not depend on how output was once normalized. Cursors are per (agent session, terminal session), advanced only by the serving read and reset by a new incarnation; a read reports `liveness` (the manager's verdict, never inferred from the content), `delta`, and `skippedBytes` - a count of what it did not return, never an offer to re-serve it. `manager.readOutput` grants nothing - `hasEdge` is still the call-time check - and `TERMINAL_CHANNELS.scrollbackRemove` calls `forgetSession` so a retired node stops being readable. See `tests/terminal-output-tail.test.ts`.
- How an agent reaches that read is `src/main/terminal-context-mcp.ts`: a Toucan-hosted MCP server with one `read_terminal_output` tool, spoken as stateless streamable-HTTP JSON-RPC (always-JSON responses) on a 127.0.0.1 listener that binds *lazily* - no edge anywhere, no port open. It is hand-rolled rather than `@modelcontextprotocol/sdk` on purpose: the tools-only surface is five methods, and the test compile's CommonJS resolution cannot see that SDK's exports-map-only subpaths. Both pinned adapters were verified to accept `type: 'http'` `mcpServers` entries (codex-acp maps them to `{url, http_headers}` and rejects SSE; claude-agent-acp forwards `{url, headers}`), which is what settled the plan's transport question. The session manager asks the injected `terminalContext.serverFor` per creation and puts the entry on `session/new`/`session/load` only when the chat node has an edge right then - every other session carries zero extra tokens - reporting it back as `AgentCreateResult.terminalContext`, launch-time truth like `routineDelegation`. Authorization is a per-agent bearer token minted with the grant: it names the calling agent (the read cursor is per reader) and shuts out any stray local process, and every call still checks `hasEdge` at call time, so a revoked edge refuses immediately while the definition merely lingers until the next natural resume. An edge drawn onto a *running* session adopts by restart at a safe boundary, the worktree-claim pattern but for both providers since the cwd never changes: `planTerminalContextAdoptions`/`adoptTerminalContext` in `src/renderer/src/terminal-context-edges.ts` compare the live edge set against the launch-time truth each session reports up through `onTerminalContext`, fire only at `idle`/`result` with a `conversationId` to resume, and bump `terminalContextNonce` (runtime-only node data), which restarts the session effect as `resume`. See `tests/terminal-context-mcp.test.ts`, `tests/acp-session-manager-mcp.test.ts` and the adoption cases in `tests/terminal-context-edges.test.ts`.
- `.terminal-node` (canvas chat nodes) is `overflow: hidden`, so any dropdown/menu anchored inside with CSS `position: absolute` clips at that ancestor's edge. `SelectorPicker` in `src/renderer/src/ChatNode.tsx` (the Provider/Model/Effort/Permissions pickers) instead portals its menu to `document.body` and positions it in JS against the trigger button's viewport rect via `computeNodePickerMenuPosition` in `src/renderer/src/node-picker-menu-position.ts`, clamped to stay fully on-screen. Follow the same portal pattern for any new floating menu inside these containers rather than CSS anchoring.
- The app has exactly one scrollbar. `:root` in `src/renderer/src/styles.css` declares `scrollbar-color: #3b4553 transparent` and `scrollbar-width: thin`; both properties inherit, so every scroll container - panels, dialogs, menus, the chat transcript, file nodes, composer, terminal viewport - already has the chat-node scrollbar and must never redeclare one. A new scrollable surface needs no scrollbar styling at all, and a surface showing the platform default scrollbar means something above it overrode the inherited value rather than that it forgot to opt in. `tests/scrollbar-styling.test.ts` locks both halves: the root declaration and the absence of any per-component redeclaration.
- `promptWhenIdle` in `src/main/acp-session-manager.ts` uses the adapters' advertised `_session/steering` extension while a turn is working, so accepted follow-ups are injected exactly once and the adapter observes them at its next safe boundary without replaying or cancelling the turn; a single non-yielding tool can delay that boundary. Adapters without steering fall back to the non-expiring FIFO `PromptWakeGate` in `src/main/prompt-wake-gate.ts`, drained after turn completion/Stop.
- `withStallGuard`/`StallTimeoutError` (`src/shared/stall-guard.ts`) is the shared "bound a promise that might never settle" primitive for operations that genuinely have a deadline, such as `VoiceInput` model load/start and the Codex account-rate-limit read. Never wrap a whole ACP `session/prompt` turn in it: a turn spans every tool call and has no wall-clock deadline, so elapsed time cannot distinguish healthy long-running work from a wedge. `settleAgentTurn` in `src/main/acp-session-manager.ts` waits for the provider's real completion/rejection or explicit cancellation; manual Stop and the renderer's non-destructive inactivity indicator are the recovery paths.
- Durable writes have one home: `src/main/durable-file.ts` owns temp-write-then-rename (async and sync, fsync semantics included), and `src/main/durable-json-store.ts` is the one store behind main's simple single-file JSON stores (conversation titles, brain-dump capture, terminal liveness, remote-access settings, adapter selection) - each of those is a parse predicate plus a fallback, never its own rename/fsync/queue. `workspace-store.ts` (backup promotion) and `terminal-scrollback-store.ts` (pending marker, deliberately unfsynced per output chunk) keep their own protocols composed from `durable-file` primitives; do not fold them into the generic store. Serialized writes share `createSerialQueue` in `src/main/serial-queue.ts`. See `tests/durable-file.test.ts`, `tests/durable-json-store.test.ts` and `tests/serial-queue.test.ts`.
- `createWorkspaceStore` in `src/main/workspace-store.ts` owns all workspace-canvas persistence. `save()` serializes concurrent calls through an internal promise queue, validates the incoming state, writes it to a temp file via the shared `writeFileDurably` helper (fsynced, and unlinked again on any write failure), promotes the current (still-valid) primary snapshot to a single bounded `<path>.backup` recovery copy, then atomically renames the temp file onto the primary (also unlinking the temp file if that rename choreography fails) — so a crash or a failed save at any point leaves either the untouched old primary+backup or a fully-written new primary, never a torn file or a leaked temp file. `load()` returns a `WorkspaceLoadResult` (`state`, `recovered`, `unrecoverable`): it falls back to the backup and self-heals the primary when the primary is missing/corrupt (`recovered: true`, surfaced by `App.tsx`'s "Recovered from backup" indicator), and when neither primary nor backup validates but at least one of those files exists on disk, it reports `unrecoverable: true` with `state: null` instead of the fresh-install case (`unrecoverable: false`) — callers must never silently seed and autosave a fresh default over `unrecoverable: true`, since that would permanently destroy the last damaged-but-potentially-recoverable copy. `App.tsx` enforces this: on `unrecoverable`, it shows a non-dismissable warning dialog and only seeds a fresh workspace after the user explicitly acknowledges it. Both primary and backup reads go through `parseWorkspaceState`, so schema migrations apply uniformly to either. See `tests/workspace-store.test.ts` for the interruption/corruption/concurrency/unrecoverable scenarios this guarantees.
- Both ACP adapters replay a resumed session as `session/update` notifications during `session/load`. `src/main/acp-session-manager.ts` buffers that finite stream into `AgentCreateResult.replay`, and `useAgentConversation` folds it through the live event handler; keep replay off the separate `agent:event` IPC channel, where renderer startup can lose it. That folding is not the hook's: `foldAgentEvent`/`applyAgentCreateResult` in `src/shared/agent-transcript.ts` is the pure, runtime-neutral reducer every host (renderer today; main/remote later) runs over the same `AgentEvent` stream to derive an identical transcript, and it is the *single writer* of conversation state: a client's own inputs (optimistic prompt start, selector clicks, answered approvals/questions, delivery flags) fold through the same reducer as `LocalAgentEvent`s, with `statusOrigin` encoding the one precedence rule - main wins for anything that crossed the seam (issue #162 retired the hook's read-back guards). The hook is a thin wrapper owning only renderer-local delivery state (draft, outbox, optimistic-send echo dedupe) and IPC - new transcript-shaped state, and any write to it, belongs in the reducer, not in the hook (`tests/agent-transcript.test.ts`). Codex distinguishes commentary from final text only through replay-stable `_meta.codex.phase`, preserved as `AgentEvent.presentation`. For unphased assistant text (including Claude), `src/shared/assistant-presentation.ts` presents it as provisional progress and promotes only the last message of each completed live or replayed turn to final. `isFinalAssistantMessage` is the shared gate for final-only title, decision, and result-attention behavior; progress remains available in transcript history and worktree handoffs even when Focus hides it. Claude reasoning remains the separate `agent_thought_chunk` path. `isInternalNotificationText` filters Claude's synthetic supervision injections where Toucan consumes `session/update`. See `tests/assistant-presentation.test.ts`, `tests/restored-chat-transcript.dom.test.tsx`, and `tests/acp-session-manager-replay.test.ts`. Live events are never sender-bound: `acp-session-manager.ts` publishes every `AgentEvent` to the `AgentEventBroker` (`src/main/agent-event-broker.ts`, injected at the composition root), which folds each event into a per-session main-process transcript snapshot and fans it out - the creating renderer is only subscriber #1, and `subscribe` returns snapshot + gap-free live tail atomically for late joiners (the remote server's join contract). Replay is `fold`ed into the snapshot but never fanned out, `stop` closes the channel unconditionally so the renderer's kill-then-recreate cycle cannot stack owner subscriptions, and answering an approval publishes `approval_resolved` so every subscriber retires the same pending card. Adapter stderr is published as `status: 'starting'` progress only while `RunningAgent.opening` holds (launch until `openSession` settles) - its docblock explains the pipe-ordering race behind issue #158. See `tests/agent-event-broker.test.ts` and `tests/acp-session-manager-broker.test.ts`.
- ACP auth-required detection has one home, `isAuthRequired` in `src/main/acp-session-manager.ts`, feeding both `promptFailure` (mid-conversation) and `openSession`'s catch (session creation/resume) so every auth failure reaches the same `{ type: 'auth', methods }` sign-in UI.
- There are two test runners: `tests/**/*.test.ts` (compiled by `tsc -p tsconfig.test.json`, run with `node --test`) covers non-UI logic and has no DOM; `tests/**/*.dom.test.tsx` (Vitest + jsdom + `@testing-library/react`, config in `vitest.config.ts`, setup in `tests/dom/setup.ts`) actually renders renderer components/hooks.
- Transcript markdown lives in `src/renderer/src/MarkdownMessage.tsx` (GFM via `remark-gfm`), and it re-renders on every streaming chunk. Syntax highlighting therefore must not be a rehype plugin — that would re-tokenize every code block in the message per chunk. `pre` is replaced by a `React.memo`'d `CodeBlock` keyed on its own text, so only the block still streaming is re-highlighted; keep that shape for any future per-block work. What a Markdown link *is* has one home, `classifyMarkdownLink` in `src/shared/local-file-link.ts`: a web URL, an absolute local path, or nothing openable at all. It is what the transcript and the brain-dump reader both classify through (`classifyBrainDumpLink` adds only the private topic scheme on top of it); a rendered file node and a ticket body deliberately still offer web links only, so a local link there is inert. It is the gate, not a convenience - react-markdown's sanitizer blanks `file:` and reads `D:/x` as scheme `d:`, so these surfaces pass `urlTransform={keepHref}` and rely on the classifier instead, rendering anything `unsupported` (relative links, anchors, `javascript:`, unknown schemes) as inert text with no `href`. It recognizes every form an agent writes one path in - either separator, a leading `/D:`, `file:` URLs, UNC, angle-bracketed - and decodes *before* classifying, because `mdast` runs every link URL through `normalizeUri` and a `%5C` separator is not recognizable as a path. `//host/x` is deliberately read as a protocol-relative URL rather than a share. Web URLs go through `terminalApi.openExternal` → the `shell:open-external` handler, which forwards http/https only; a plain `<a>` would navigate the app window away. A local path splits on whether Toucan has a view for it: anything it can render opens as a file node on the canvas (`OpenFileContext`), which reads bytes and executes nothing, and only the inert media `opensInSystemViewer` lists is handed to the OS through `shell:open-local-file` → `createLocalFileOpener` in `src/main/local-file-open.ts`. `svg` is deliberately not on that list - the OS opens one in a browser, which runs the script an SVG may carry. Which of those a link does, and the tooltip saying so, are one decision in `src/renderer/src/markdown-link-action.ts`, and only a web link carries a real `href`: a click is intercepted but a middle-click or a link-drag is not, and neither may hand the window a local path to navigate to. That is the one path action that can *run* something, so it is narrow twice over: containment through the shared `createWorkspaceContainment` (`src/main/workspace-containment.ts`, also the fail-closed guard behind `file-view.ts`) and the same media allowlist re-checked in main, because a renderer is not what a privilege boundary may trust. Every refusal is returned and shown beside the link - a local link that silently did nothing was issue #175. See `tests/local-file-link.test.ts`, `tests/local-file-open.test.ts` and `tests/chat-markdown.dom.test.tsx`.
- Past conversations are browsable and resumable independently of any node: `src/main/conversation-history.ts` enumerates both providers' transcripts for a set of working directories (a project checkout plus its worktrees) and `ConversationHistoryDialog.tsx` (canvas context menu -> History) opens the picked one as a node with `launchMode: 'resume'`. Enumeration is deliberately two-phase - candidates cost a directory entry plus, for Codex, one head read cached by path (a `session_meta` line never changes), and only the requested page's transcripts are read in full - so a project with hundreds of transcripts stays responsive. Claude project folders are matched case-insensitively against `encodeClaudeProjectDirectory` because the same checkout reaches the CLI under either drive-letter case; Codex subagent rollouts (`thread_source: 'subagent'`) are excluded because they are not resumable conversations. A row whose transcript has since been deleted is reported in place via `conversationApi.exists` rather than opening a resume that cannot find its conversation. `@agentclientprotocol/codex-acp` is held at an exact version in `package.json` rather than a range, because what an ACP adapter does to a resume is not something the suite can reach: it needs a live Codex process replaying a transcript. Upgrade it deliberately, and confirm afterwards that a Codex conversation opened from History still loads its content - Codex `0.147.0` once broke exactly that, rejecting history opened while another client owned the thread as `already has an active writer`. Verified working on codex-acp `1.8.0`/Codex `0.152.1` (2026-09-05). See `tests/conversation-history.test.ts` and `tests/conversation-history-dialog.dom.test.tsx`.
- Conversation titles are local and durable: `deriveConversationTitle` in `src/shared/conversation-title.ts` derives one stable title from enough dialogue without a model call (zero tokens/account budget), while `src/main/conversation-title-store.ts` keeps provider/session-keyed metadata outside provider-owned transcripts. Generated writes are first-write-wins; manual writes may rename repeatedly and always outrank later generation. `WorkspaceTerminalNode.titleSource` preserves the node header/sidebar identity, and history consults the same durable metadata. Which messages a title may be derived *from* is `generatedConversationTitle` in the same shared module - the user's messages plus the assistant's final answers only, so neither progress prose nor reasoning can title a conversation; the chat node and the session outcome index both call it rather than filtering their own. Keep title normalization shared and never rewrite provider transcript files. See `tests/conversation-title.test.ts` and `tests/conversation-title-store.test.ts`.
- The session outcome index is what every agent conversation leaves behind for the next one: one compact Markdown record per conversation under `<userData>\session-outcomes\`, keyed `(provider, conversationId)` like conversation titles, because conversations outlive canvas nodes. Capture is pure *extraction* and costs zero tokens (`src/shared/session-outcome.ts`, same bias as `conversation-title.ts`): the first user message is the task, the latest final assistant message the last result. What counts as the agent having *answered* is not re-decided here - `generatedConversationTitle` moved into `shared/conversation-title.ts` so the renderer's title and the record's read `isFinalAssistantMessage` identically; relabelling a `thought` as an assistant message would pass that gate (thoughts carry no `presentation`) and title a conversation off its own reasoning. The title itself is *read* from `conversation-title-store.ts` rather than derived, so a record can never contradict a manual rename. It hangs off the broker as subscriber #2 (`src/main/session-outcome-indexer.ts`, injected into `AcpSessionManager` like the broker itself), retired by the same `broker.close`, which is what covers phone-driven turns for free - main is where every turn passes, whatever drove it. The capture point is the **turn boundary**, not the end of the session: sessions outlive processes, so a record written at close alone would be lost to every restart, and `turn_complete`/`turn_failed`/`turn_cancelled` all upsert the same file. The snapshot and context are read *in the subscriber* and carried into the queued write - reading them when the write finally runs loses the last turn of any session stopped while its capture is still on disk, which is the record most worth keeping. Two constraints belong in the shared module rather than at any write site: the excerpts are hard-capped with the ellipsis inside the budget (`SESSION_OUTCOME_EXCERPT_LIMIT`), because the index only pays for itself if an agent can grep hundreds of records into one context window; and the conversation id is sanitised into the filename, so no provider id can escape the directory. Everything else is re-derived from the transcript each turn - only `startedAt` and the write set (its paths and its omitted count) are carried over - so a record cannot drift from what it describes, and a damaged one is simply rewritten. `turns` counts user messages rather than boundaries so a resume re-derives it instead of double-counting replay; a steered follow-up therefore counts as an ask of its own. The write set is the deliberate exception to re-derivation, because no snapshot reports what an exited process wrote: the indexer accumulates it at the session manager's `recordWrittenLocations` seam (which is also what keeps reads and searches out - `isFileWritingToolKind`) and merges it with the previous record, deliberately *not* off the 100-entry `recentWrites` ring, which is bounded for a different job and drops a long session's early writes. That seam is why `recordWrittenLocations` returns its paths and the call site forwards them in two statements: `a?.b(f())` would skip `f()` entirely wherever no index is wired, taking the session's own write attribution with it. `sessionOutcomeWriteSet` is the one place the set is deduped, ordered newest-last and clipped, and `sessionOutcomeFiles` the one place it is *capped* - two functions on purpose, because the indexer's accumulator must stay uncapped: capping it too would throw away the very paths the record's omitted count is derived from, and a session's list would then look complete at sixteen however many hundred it wrote. A capped list ends on `sessionOutcomeFilesOmittedMarker` ("… and at least N older files omitted"), parsed back as a count rather than a path, because an unmarked truncation is the file list answering "nothing has touched this" for a file the conversation rewrote. "At least" is load-bearing: `filesOmitted` is `max(what the record already counted, what this merge dropped)`, exact within one process and a floor across a restart, since a resumed session cannot tell its own writes from the paths an earlier one already dropped. Failures are re-derived from the transcript's own `outcomes` in the shared `AgentTurnOutcome` shape. `status` is `active` until the session ends, and ending has *two* routes: the broker channel being retired (`stop`, so the index is a second consumer of the `closed` hook) and the adapter exiting on its own, which retires no channel and reaches `SessionOutcomeWatch.finalize` from `child.on('exit')` instead. Finalizing is deliberately a status transition on the record the last boundary already wrote, not another extraction - that is what lets it run *synchronously*, which is the only thing that survives `before-quit` (every session is killed and the process is gone before a promise settles); it also queues an async pass, because a capture still on disk would otherwise write `active` back over it. `completed` needs the last turn to have both finished cleanly and answered, where answered means `answeredLatestAsk` - a final assistant message after the *latest* user message, not anywhere in the transcript, or a conversation answered once and then asked again would report itself finished. Every cap (`SESSION_OUTCOME_FILES_LIMIT`, `_PATH_LIMIT`, `_FAILURE_LIMIT`, `_FAILURE_MESSAGE_LIMIT`) is chosen against one ceiling, `SESSION_OUTCOME_SIZE_BUDGET`, which a test holds honest for the worst case rather than the typical one. Writes go through `writeSnapshotAtomically`, serialized per store, and every writer goes through `store.update` rather than a bare read-then-write: each one is a read-modify-write (a capture merges the write set it inherited, finalizing settles a status) and two sessions can hold one conversation at once - retiring a node and resuming it are a gesture apart - so a read outside the queue lets the slower writer put its stale copy back on top. Deliberately **no UI and no IPC**: humans ask an agent to read the folder. `worktreeId` comes from the persisted canvas snapshot at the composition root, the only main-side place a node's worktree association exists. Retrieval is therefore nothing but a sandbox grant plus a sentence: every session gets the outcomes directory in its `additionalDirectories` (the brain-dump library's mechanism, and the whole of "no permission prompt", since the folder is under userData and outside every project `cwd`) and carries `sessionOutcomeIndexInstruction` in its context - on `_meta.systemPrompt` for Claude, in `CODEX_CONFIG.developer_instructions` for Codex. Both carriers *append* rather than assign (`withSessionInstruction` here, `withCodexSessionConfig` in `shared/codex-config.ts`, which the delegation policy also layers through), because a session gets one system prompt and several things want a line in it. The pointer lives beside `renderSessionOutcome` and names every field it writes, so a field renamed on one side only would send every future session grepping for a line that no longer exists. It teaches a **two-stage read** - grep `project:` to name the files, then open only what is worth opening - because that, not the per-record cap, is what makes the index worth consulting by default: a screenful of 20 records is ~5.4k tokens read in full and ~1.3k at stage one (measured in `docs/plans/session-outcome-index.md`, which is also where the caps tightened against those numbers are recorded). Sessions can write to the folder, and nothing prevents one scribbling in it: that is survivable rather than guarded, because an unreadable record reads as absent and the next turn boundary rewrites it in full. The live check is `node scripts/verify-outcome-retrieval.mjs [claude|codex]`, deliberately outside `npm test` since it spends account tokens. Hygiene is two rules, both stated purely in the shared module and both applied at the indexer because each needs something the store cannot see. A conversation with no writes and fewer than `SESSION_OUTCOME_TRIVIAL_TURNS` asks (`isTrivialSessionOutcome`) leaves nothing behind - but its record is written every turn regardless and *deleted* at `finalize`, because that record is what carries `startedAt` and the write set between turns, and only the end of a session settles the verdict; deletion runs on both finalize passes, and the queued one re-reads rather than trusting the synchronous one, since a capture landing in between may have earned the record. And the directory is capped at `SESSION_OUTCOME_RECORD_CAP`, `prunableSessionOutcomes` dropping the least recently updated (an unreadable record has no timestamp and goes first) - run only after a record is *created*, the one moment the count can grow, off the cheap `store.keys()` listing so the full directory read costs once per new conversation rather than once per turn. What pruning must never take is a conversation still being written to, and that is the indexer's live set rather than the record's `status`, which only means no end was observed and so reads identically for a node dormant since last week; it is refcounted per watch, because retiring a node and resuming it leave two sessions holding one conversation and the first release must not speak for the second. Live records still count toward the cap, so an index of nothing but live sessions stays over it until they end. Both hygiene verdicts are taken from the freshest thing available rather than from the file: finalizing calls a conversation trivial only when the record *and* the last boundary this session saw both say so, since a capture still queued at `before-quit` never lands and a stale file would erase the conversation it belongs to. - The composer is a prompt editor (ownership in `docs/architecture.md`): a change to how the text behaves lands in `usePromptEditor` (`src/renderer/src/use-prompt-editor.ts`), never in the rendering-only `Composer` in `ChatNode.tsx`. The decisions themselves live in small pure modules the hook wires together: `composer-keys.ts` (one function decides send vs newline vs history-walk from the workspace-wide `ComposerSendKey`), `prompt-history.ts` (session prompt ring, walked with the arrows from an empty composer), `composer-autosize.ts` (growth bounds), `slash-command-completion.ts` (when a `/` token is a command, how the list narrows, what accepting inserts and where the caret lands), and `prompt-outbox.ts`. `file-mention-completion.ts` is the same shape for `@`: how the index narrows and ranks, and what accepting inserts. What counts as a token at all is one rule both share, `tokenOpeningWord` in `completion-token.ts`: a sigil starts a token only where a word starts - the draft's start or after whitespace - so `src/main` and `morgan@example.com` stay prose while `now run /code-review` opens the list. Deliberately whitespace and nothing else (`(/rev` is left alone), and deliberately _not_ anchored to the line start: agents honour `/<name>` as an invocation anywhere in a prompt, so a picker that only opened a line would refuse exactly the mid-prompt invocations captains write (issue #140). The agent CLI, though, expands a command only when the prompt _starts_ with it - anywhere else the literal text reaches the model, which can only reach for the `Skill` tool, and a `disable-model-invocation` skill is precisely what that tool's registry omits, so the invocation dead-ends in a "no such skill" non-answer (issue #160). `hoistSlashCommand` closes that gap on send: the command moves to the front with the rest of its own line - accepting parks the caret right after the command, so what follows it there is what was typed as its arguments - and the prose it was lifted out of drops below. It reads its token through the same `tokenOpeningWord`, so it can never fire where the picker wouldn't have offered, and a draft already opening with its command is only trimmed of the leading whitespace that would push it off offset 0. Only the command the captain actually took from the menu moves: a name the draft merely mentions ("what does `/implement-in-worktree` do?") is prose, and hoisting that would invoke it. The editor tracks that acceptance in its own `acceptedCommand` state, not `SlashCompletionState.acceptedQuery` - that one belongs to a single token and is spent the moment the caret leaves it, which is exactly when the captain starts typing the command's arguments - and spends it when the draft is sent. One consequence worth knowing: `invokesWorktreeSkill` in `src/shared/worktree-handoff.ts` recognises the skill only on the first line by design, and the hoist is what puts a mid-prompt `/implement-in-worktree` there, so it now takes the up-front handoff path instead of falling back to claimed discovery. Both pickers render through one `CompletionMenu` in `PromptTextarea.tsx` and only one is ever open (`activePicker` in the hook) - the shared token rule makes the two mutually exclusive, since a word start is either a `/` or an `@`. A picker's per-token memory (what Escape dismissed, what was just accepted) must be forgotten the moment the draft stops offering that token, or the next identical token typed in its place is silently refused. The slash list is never hardcoded: it is whatever the session advertised through ACP's `available_commands_update`, normalized by `simplifyAvailableCommands` in `src/main/acp-session-manager.ts` and cached there so reopening an agent isn't left blank. The outbox is the load-bearing one: a follow-up submitted while a turn is working is held _in the renderer_, never handed to `promptWhenIdle`, because a prompt that has crossed into the adapter (steered into the running turn, or parked in the main-process `PromptWakeGate`) can no longer be taken back — that hold is what makes Edit/Withdraw mean anything, and "Send now" is the explicit opt-in back into steering. Decision answers and `sendMessage` deliberately bypass the outbox and still steer immediately, since the agent is actively waiting on them. The outbox drains one prompt per idle turn. Drafts belong to the node (`WorkspaceTerminalNode.draft`), not the ACP session, so they outlive resize, collapse and reload; the prompt editor debounces them upward through `onDraftChange`. Toucan has no editor, so "open/recent" is the set of files the agent has already read or written this conversation (activity `locations`) - that is the picker's top band and the only signal the composer gives about what the agent can already see. Accepting inserts the root-relative path as plain text rather than an ACP `resource_link`: both installed adapters flatten a resource link back into text before the model sees it, so the block would buy nothing and cost the composer's plain-text draft, prompt history and echo matching. - The ticket board (`src/renderer/src/TicketBoardPanel.tsx`) is a projection, never a copy: a dropped or deleted card changes on screen only after the write is awaited and the sources re-listed. It is a second docked panel built on the brain-dump panel's rules (sibling of `.canvas-region`, lazily mounted then `hidden`, optional `WorkspaceState.ticketBoardPanel`), and everything above `TicketSource` in `src/shared/ticket-source.ts` knows only cards, so a new tracker is another source and nothing else. Capabilities are what a source declares: `setStatus` is what lets a column accept a drop, `remove` what puts Delete on a card, `removalNote` where the git-checkout wording comes from. The watcher never creates a tickets folder to watch it, and `ticket-directory.ts` ignores a `ticketsDirectory` that leaves the checkout. That folder is a per-project setting the user edits in `ProjectSettingsDialog` (the gear on a sidebar row); main resolves it from the *persisted* snapshot per call, so the board re-lists on `revision`, which `App.tsx` advances only once the save has landed - and the watcher re-resolves the folder on every `watchProject`, closing the handle on the folder the project has left. Session chips on cards come from files a chat node actually wrote (`ticket-activity.ts`), matched by path identity, never inferred from a status. The board is three panes - states, the selected state's tickets, the selected ticket's body - and `ticket-board-panes.ts` owns every decision behind them: a state row is only ever _fallen back to_, never committed, because the very first render happens before any source has answered; the open ticket is keyed by `ticketCardKey`, so a drop that moves it drags the state selection along instead of closing the detail; and a panel too narrow for three panes shows the detail _instead of_ the list, which is why the detail owes a back affordance in that mode only. The drop target is a state row, and Left/Right mean "another pane" everywhere except on a card's grip, where they still mean "another state" - the grip stops the press from being read twice. The schema is enforced on the *writing* side too, and by Toucan rather than by a provider hook - any skill in either provider can drop a file into that folder, including through a shell redirect, so the one place that covers all of them is Toucan noticing afterwards. The watcher's `onChanged` re-lists the folder through the very listing the board renders (so generation and rendering cannot be held to two different schemas), `src/shared/ticket-conformance.ts` decides who to tell, and `src/main/ticket-steering.ts` delivers it through `promptWhenIdle` - steered into a working turn, queued as the next prompt where the adapter cannot steer. Attribution is the tool-call `locations` of *writing* calls only (`isFileWritingToolKind`; having read a file is not having produced it), kept as a bounded per-session ring in `acp-session-manager.ts` and resolved against the session's own `cwd` as they arrive; one writer is steered, no writer steers nobody (a hand edit is the board diagnostic's business alone), several means the most recent. The dedupe record is written at hand-off rather than at delivery, because a queued message does not land until the turn in flight ends and every watcher tick in between would otherwise re-steer; a delivery that comes back refused undoes its own record so the next change retries. The module docblocks carry the rest; tests are `tests/ticket-*.test.ts`, `tests/ticket-board-panel.dom.test.tsx` and `tests/ticket-session-cards.dom.test.tsx`.

- A file node (`src/renderer/src/FileNode.tsx`, type `fileNode`, persisted as the optional `WorkspaceState.files`) is layout, not a session: a node whose file has gone keeps its place and reports "not on disk" itself, only a vanished project drops it, and closing one is filtered out of `rememberClosedSessionNodes` so it neither becomes a Ctrl+Shift+T target nor wipes the stack the way a worktree close does. Every file node is built through `createFileCanvasNode` in `canvas-workspace.ts`, and its Rendered/Raw choice is node data (`onViewModeChange`), never component state, so it survives a restart. The renderer never reads or writes bytes: `src/main/file-view.ts` is the only reader and writer and it **fails closed** - a path is readable or writable only when its _real_ path (links resolved) lies inside a registered project checkout or worktree, with the roots re-read from the snapshot per call; oversize reads are `truncated` rather than refused. That containment check and `pathIdentity` in `src/shared/paths.ts` answer two different questions and must not be swapped: `pathIdentity` is the one rule for "are these two strings the same file?" (separator runs collapsed, UNC prefix preserved, `toLocaleLowerCase('en-US')` because a Turkish host would otherwise lowercase a drive letter's `I` to `ı`) and is what every match and display comparison runs through, while only `createWorkspaceContainment` may decide whether a path is *inside* a root, because only it resolves links. A caller needing `..` resolved layers `node:path` over the shared rule (`resolvedPathIdentity` in `brain-dump-capture.ts`) rather than writing a second one. See `tests/paths.test.ts`. Changes are watched through the file's _directory_, because editors and agents rename a temporary over the file and a watch on the inode misses that; holds are counted per window and path, so two nodes on one file survive either closing, and an `unwatch` that lands while the roots are still being checked still wins. The raw view is a CodeMirror 6 editor (`CodeEditor.tsx`, grammar picked by `@codemirror/language-data` from the file name, tokens themed through `classHighlighter`'s `tok-*` classes in `styles.css`; the transcript's code blocks still use lowlight); a truncated or binary read is read-only because saving a partial view would write it back as the whole file. Editing keeps **disk as the truth**: the draft and the `mtime` it was based on live in the pure `FileEditState` reducers in `file-node.ts`, a save hands that `baseMtime` to `write`, which refuses a changed file as `conflict` after replacing atomically through a temporary, and a change the watcher reports under a draft (or a conflict verdict from a save) becomes a banner offering Reload or Keep - the draft is never replaced and the file is never overwritten silently. `src/main/file-formatter.ts` applies bundled Prettier before every file-node save when its built-in parsers support the path, honoring the nearest `.prettierrc.json` or `package.json#prettier` and `.prettierignore`; it deliberately strips plugins and never loads JavaScript config, because saving an untrusted checkout must not execute its code in main. Formatting is best-effort: unsupported/ignored files pass through, parse/config errors save unchanged with a visible warning, and `file-view.ts` rechecks the base `mtime` after asynchronous formatting before its atomic replacement. The write result carries the exact saved content back so the editor adopts formatting without losing keystrokes entered mid-save. The node's own save is recognised by the `mtime` the write returned, so the watcher event it causes is not a conflict. Unsaved drafts are component state and do not survive a restart. Files arrive two ways, both through `addFileNode` in `App.tsx`: the context menu's `FilePickerDialog` (the composer's `@` index, files only) and "Open" on a transcript file card, offered only where `OpenFileContext` is provided and filed under the deepest checkout or worktree containing the path (`projectOwningPath`). Ctrl+F searches the node the reader is on, and the canvas owns that key: `nodeSearchKeyAction` in `node-search.ts` yields to text fields (CodeMirror's editable content binds Ctrl+F itself) and to open dialogs, `App.tsx` resolves which node it means - the one the key came from, else a lone selected one - and names it through `NodeSearchContext`. What search _is_ belongs to the view: rendered prose gets the shared `FindBar` (also for AI-chat and diff nodes later), the raw view gets `@codemirror/search`, because CodeMirror virtualizes its viewport and a DOM search would find only the screens it has rendered. `FindBar` never wraps matches in elements - the surfaces it searches are React-rendered, so the next render would undo it - and paints them through the CSS Custom Highlight API instead, from `Range`s that touch nothing; a browser without the API (and jsdom) simply shows no highlighting while the count and navigation still work. CodeMirror mounts under jsdom only with the range stubs in `tests/dom/codemirror-jsdom.ts`, loaded by the Vitest setup. See `tests/file-view.test.ts`, `tests/file-view-ipc.test.ts`, `tests/file-node.test.ts`, `tests/file-node.dom.test.tsx`, `tests/file-open-entry-points.dom.test.tsx`, `tests/node-search.test.ts` and `tests/node-find-bar.dom.test.tsx`.

- Debounced directory watching is one mechanism, `createWatchedDirectories` in `src/main/watched-directories.ts`: per-key debounce with unref'd timers, subscribed owners plus counted per-key holds with destroyed-owner pruning, the null-filename refresh rule, and watcher error swallowing, with `WatchDirectory` injected. `brain-dump-watcher.ts`, `ticket-watcher.ts` and the watch inside `file-view.ts` are policies over it - key/payload, filename filter, and release (brain-dump never releases; tickets close all when `hasOwners()` goes false; file-view closes per key through `onUnheld`) - so a fourth watcher is a policy, not a copy, and a debounce or pruning bug is fixed once. A settled key also reports through `onPublish`, which is how a main-side reader of the same change (ticket conformance) hangs off a watch without becoming a subscriber - an owner that never reports itself destroyed would pin `hasOwners()` true and hold every watch handle for the life of the process. See `tests/watched-directories.test.ts`.

- A canvas node kind's *mechanical* concerns are one table entry, `CANVAS_NODE_KINDS` in `src/renderer/src/canvas-workspace.ts`: which `WorkspaceState` array it persists into and whether that field may be absent, its type guard, its serializer (which owns the size it falls back to), and its restore-and-prune. `restoreCanvasWorkspace` and `serializeCanvasNodes` are one loop each over that table - so "drop it if its project is gone" is written once, for every kind, in the loop rather than in four restores - and `isWorkspaceState`'s mirror table on the main side (`CANVAS_NODE_VALIDATORS` in `workspace-store.ts`) is what validates the same fields across the privilege seam. A fifth kind is one entry in each of those two tables, one field on `WorkspaceState` plus its name in `CanvasNodeStateField`, one `CanvasNode` union member and its component - and `tests/workspace-store.test.ts` holds the two tables to the same fields so a kind cannot be persisted without being validated, while `tests/canvas-workspace.test.ts` proves an entry alone carries a kind through restore, pruning and serialization by registering a fixture one. Deliberately *only* the mechanical concerns: the callback bags, terminal status, scrollback teardown, attention and the remote projection stay where they are, because describing them here would turn every entry into optional hooks one kind uses. Beside it, `CREATE_NODE_ACTIONS` is the one table behind the context menu, the Ctrl shortcuts, the hint labels and the size a new node is centred by - an action with no row there is a compile error, not an `undefined` size (its icons are the only per-action thing left in `App.tsx`, since that table must stay importable by the non-DOM test runner). Three rules that were written twice now have one home each: `createWorktreeCanvasNode` is the only worktree-node factory (`deletable: false` is why that matters - the Delete key must never orphan a directory git still knows about), `rememberClosedSessionNodes` alone decides what closing each kind means to the reopen stack (a layout node is neither a target nor a wipe, so callers hand it every removed node unfiltered), and `withProjectColor` fans a project's colour across every kind that denormalises it.

- A diff node (`src/renderer/src/DiffNode.tsx`, type `diffNode`, persisted as the optional `WorkspaceState.diffs`) reviews one checkout against its recorded base - a worktree against its `baseRef`, or the primary checkout against `HEAD`, which is the only base a checkout with no recorded origin has. Diffs come from git, never from transcripts: `WorktreeManager.diff` in `src/main/git-worktree.ts` reads the file list and `diffFile` reads hunks for one file at a time, so a large review never costs a whole-tree diff; both hand git's `-z` machine output to the pure `src/shared/git-diff.ts`, the one place those formats are understood. `diff-node.ts` maps a hunk onto the transcript's `FileOperationBlock`, so hunks render through the same `FileOperationBlockView` as file cards and inherit their Open/Copy/Reveal path row. The node's refresh effect must never depend on the whole `data` object: selecting a file rebuilds it, and re-running the effect on that would re-read the list and blank the pane on every click. Every diff node is built through `createDiffCanvasNode`; the open file is node data (`onSelectDiffPath`) so a restart reopens the same review, and it is retained across a refresh only while that file is still changed. Polling runs on the worktree badge's tick and only while the node is on screen and the app visible. It is layout, not a session (`isLayoutCanvasNode`, with file nodes): closing one never enters the reopen stack. A diff node is _not_ attached to its worktree - it runs nothing there, so it never blocks removal - and `withoutWorktree` removes it together with the worktree it reviewed, as does restore for a worktree record that has vanished. Entry points: **Diff** on the worktree node header, and the canvas context menu / Ctrl+D for the active project's primary checkout. See `tests/git-diff.test.ts`, `tests/git-worktree.test.ts`, `tests/diff-node.dom.test.tsx` and the diff cases in `tests/canvas-workspace.test.ts` and `tests/workspace-store.test.ts`.

- Fit mode is workspace state, not node state: `useNodeFit` (`src/renderer/src/use-node-fit.ts`) owns the single fitted node and its session-local restore geometry, and the decisions are pure functions in `node-fit.ts` (`requestNodeFit` restores whichever node is already fitted before fitting the next, `reflowFittedNode` recomputes geometry for a changed canvas, `exitsNodeFitMode` distinguishes a user drag/resize from React Flow's own measurement). The usable canvas is _observed_, not derived: one `ResizeObserver` on `.canvas-region` covers application resize, sidebar collapse, and the docked brain-dump panel, because all three are layout siblings - so nothing reads window size or panel state, and reflow only ever reads the viewport, never writes it. The node's `fittedToCanvas` data flag is presentation for the header action; persistence and recently-closed capture must go through `nodeBeforeTemporaryFit`, which keys on the fitted node's id so a fitted node is never saved filling the screen. See `tests/node-fit.test.ts`, `tests/node-fit-mode.dom.test.tsx` and `tests/node-fit-action.dom.test.tsx`.

- Remote access (`src/main/remote/`) is Toucan's only network surface beside the localhost-only terminal-context MCP listener (which never leaves 127.0.0.1 and binds lazily), and it is off until the user enables it. Two rules keep it honest. The pairing token is the whole authorization story - every `/api` route checks it with `pairingTokenMatches` (constant time), it is only ever read from an `Authorization: Bearer` header, and `resolveRemoteRoute` decides authorization per _route_ so a new endpoint cannot forget the gate; the static client bundle is deliberately public, because a phone cannot set a header on the navigation that loads the pairing screen. And the canvas stays the one authority on what a phone lists: `useRemoteAccess` publishes a `RemoteWorkspaceProjection` (derived by `deriveRemoteWorkspaceProjection` in `src/shared/remote-access.ts`) and the host serves the latest one - never deriving its own view of the workspace, and never stamping the clock in the renderer, since a timestamp there would defeat the dedupe that stops a node drag from publishing per frame. Reading a chat live is `WS /api/chats/:id` (`ws`, `noServer`): the upgrade runs the same token gate first - also accepting the token from the `Sec-WebSocket-Protocol` bearer entry defined in `src/shared/remote-chat.ts`, because a browser cannot set a header on an upgrade - then only admits ids the published projection lists, and each socket is one broker subscription delivering a `{snapshot}` frame then `{event}` frames (`AgentEvent` verbatim, no DTO layer). A snapshot frame is a full resync the client applies wholesale, which is what makes reconnect and mid-stream replay repair duplicate- and gap-free; the broker's `closed`/`resync` subscription hooks exist for subscribers that outlive the UI that opened them - this one, and the session outcome index, and regenerating the token or stopping the listener closes every live socket rather than stranding it. Writing back goes over the same socket and through one narrow seam, `RemoteChatSessionOperations`: a `prompt` frame is answered with a `prompt_result` for its `requestId`, always - accepted, or refused with the session manager's own reason - because a send with no verdict is the one thing a phone composer cannot recover from. Two rules make that honest. The phone's policy is **blocked with a hint, never queued and never steered**: a working session is not a send target, and the host independently refuses one, so a race surfaces as a visible error instead of an accidental nudge into a turn in flight. And the host answers at _acceptance_, not at turn end, which is why remote sends use `AcpSessionManager.startPrompt` rather than `prompt` (whose promise settles when the whole turn does, and would read a failed turn as a failed send); the turn reports itself through events like everything else. The user message itself is authored by main, not by either UI and not by the provider: neither adapter echoes a live prompt back as a `user_message_chunk` (only `session/load` replay carries user chunks, and the manager drops any live one so no client needs a dedupe of its own), so `beginTurn` - and the steering path of `promptWhenIdle` - publishes one `role: 'user'` message with a fresh `messageId` at the moment a prompt is accepted, ahead of `status: 'working'`, whatever the prompt's origin. Its text is `promptText` (the prompt's text blocks only; images stay desktop-local render state, so an image-only prompt publishes nothing). The phone therefore renders no optimistic bubble and folds that event like any other host; the desktop keeps its optimistic bubble, which carries UI metadata the event cannot, and `pendingSentRef` in `use-agent-conversation.ts` consumes the host's event as that bubble's echo by matching the composed prompt text. The phone client lives in `mobile/` (its own Vite build into `out/mobile`, run by `npm run build:mobile` after `electron-vite build`) and imports `src/shared` types only; its connection, composer and rendering decisions are the pure `mobile/src/chat-connection.ts` (which owns the draft, so "what happens to what you typed when a send fails" is testable data) and `mobile/src/chat-view.ts`, folding the tail through the same shared reducer as every other host. `promptTextProblem` in `remote-chat.ts` is run by both ends, so the composer greys its button out in the exact words the host would have refused with, and an unsent draft is retained per chat in the phone's own `localStorage` - retention, never drafts sync - because a revoked token unmounts the chat screen on its way back to pairing and the typed text has to survive that. Answering a pending request travels the same socket as its own message type - `approval` and `decision` frames, answered with an `answer_result` - and never as free text: while a request stands the phone hides the composer entirely (`composerHidden`/`pendingRequest` in `chat-connection.ts`, one decision at a time with an approval outranking a queued question set, mirroring the desktop), so nothing can bypass the channel the agent is parked on. The race between two clients is decided in one place, and it is not the UI: `resolveApproval`/`resolveElicitation` key acceptance on the session's pending-request map, so whichever answer arrives first removes the entry and answers the provider while every later one is refused with `That request was already answered.` - which is why both now return an `AgentPromptResult` instead of void. The loser does not resolve its own card either: retirement always comes from the session's `approval_resolved`/`decision_resolved` event, the same source the winner sees, so no client can retire a request the agent is still waiting on. Structured answers are bounded by the shared contract (`decisionContentProblem`, `REMOTE_CHAT_ANSWER_*` in `remote-chat.ts`) and validated strictly inbound - a value outside `AgentDecisionValue` is dropped rather than guessed at, because it ends up inside an ACP elicitation response - and the phone's form rules (mutual exclusion of a chosen option and its "Other" field, what counts as answered, when submission is gated) are the pure `mobile/src/decision-answers.ts`. The list side of the same condition reads off the attention model rather than the status, since a parked turn still reports itself as working: `chatNeedsApproval` badges `attention === 'approval'` distinctly from ordinary unread, and `pendingRequestFrom` in `chat-view.ts` is the phone's one reading of "something is pending" - the card, the hidden composer and the "Needs you" pill all derive from it. A tool permission and a structured question set are deliberately _one_ attention condition (kind `approval`, keyed on the request id, raised and retired by the same effect in `use-conversation-reporting.ts` and folded into `sidebarStatus` alike): both are the agent waiting on an answer, and a chat stalled on either has to be findable from a list. Spawning is the one remote operation that is not a session operation at all, and it is the only `POST` on this surface (`POST /api/chats`, contract in `src/shared/remote-spawn.ts`): the canvas owns node identity, geometry, working-directory resolution and launch mode, so main never mints a node - `createRemoteCanvasRequests` (`src/main/remote/canvas-requests.ts`) asks the newest live window to run `addSessionNode`, the canvas's own path, which is what makes a phone-spawned node indistinguishable from a right-clicked one (worktree spawning is deliberately not offered). The verdict is never optimistic, because the phone navigates on it: `useRemoteAccess` answers only once the new node's status settles by `spawnSettlement` - `starting` is pending, `exited`/`dormant` are the phantom-chat failures, everything else means the session exists - and every way a desktop can fail to answer (no window, a window closed mid-spawn, a renderer that never replies) is its own refusal rather than a request left open. The verdict also waits on the projection: a chat socket only admits ids the published projection lists, so the hook answers a started spawn only once the host has been handed a projection carrying it - answering sooner would hand the phone an id its very next request would be refused for. `cascadedNodePosition` in `canvas-workspace.ts` is why two spawns do not land on identical coordinates; the phone's form rules are the pure `mobile/src/new-chat.ts`, refusing in the same words `remoteChatSpawnProblem` would. Which model a chat runs on is the fourth thing a phone may drive, and it is the one whose *effect* is not reported on its own channel: a `set_model` frame gets a `model_result` verdict saying only whether the change was accepted, while the new selection reaches every client as the session's own `models` event - so the phone's picker and the desktop's are two readings of one selection rather than two copies. That makes `setModel` publishing on *every* acceptance load-bearing (`tests/acp-session-manager-model.test.ts`): an adapter may answer `session/set_config_option` without restating its selectors, and the desktop used to survive that only because it folds a `local_model_selected` of its own, so a client without one was left rendering the model the turn is not running on. The seam entry is the very `AcpSessionManager.setModel` the desktop's picker calls, so what a model is and whether this adapter exposes one stays the session manager's knowledge and its refusals travel verbatim. Nothing on the phone is optimistic about it: the control shows `AgentTranscriptState.models` and disables itself while a change is on the wire, which is why a drop mid-change says the reconnected value is the real one. **A conversation keeps one model for a whole turn**, and that is refused in `AcpSessionManager.setModel` (`MODEL_CHANGE_WHILE_BUSY` in `src/shared/agent.ts`) rather than in either picker, so both surfaces inherit one rule and both grey out in the words the refusal uses - the desktop through `modelChangeBlocked`, the phone through `modelPickerBlockedReason`. Two costs make it a refusal and not a warning: a provider's prompt cache is model-scoped, so a swap re-reads the whole conversation uncached, and a thinking block is bound to the model that produced it, so the incoming model joins the turn unable to see the reasoning behind the tool calls it must continue from. Effort and permission mode are deliberately *not* covered - those the adapter applies at its next boundary - which is why this is its own flag beside `selectorsDisabled` rather than folded into it. Picking a model **before a session exists** is the one question with no live answer, since `availableModels` is advertised by a running session: `src/shared/agent-model-catalogue.ts` is what each provider was last seen to offer, recorded by the manager's `onModelsAdvertised` seam into the durable `agent-model-catalogue-store.ts` and served to the phone's new-chat form as `GET /api/models`. It is a cache presented as a menu, so two rules hold everywhere it is used: it is **empty until a session of that provider has run** on this desktop, and a spawn naming **no** model is always valid and means "whatever the desktop would pick" - the picker's default, not an unfilled field. A named `modelId` is checked against that same catalogue for that `kind` (the two providers share no ids), exactly as a project is checked against the published projection. Marking a chat read is the second canvas request and the only client frame with no verdict at all: attention records are the canvas's and "mark read" is a canvas gesture, so a `read` frame rides the chat socket (gated by the published projection like every other frame), `RemoteChatRead` hands it to the same window seam spawning uses, and `App.tsx` applies it through `handleAttention` with `READ_ON_VIEW_KINDS` - so a phone can no more retire a pending approval by looking at it than the desktop can. Nothing is answered because nothing could be acted on: the retired badge reaches the phone as the next published projection, the surface it already polls, and a lost read costs a redundant frame later rather than a wrong answer now. When to report one is the pure `readReportKey` in `mobile/src/chat-connection.ts`, whose key moves at the two moments the desktop's own read rule fires - arriving at a live chat, and a turn ending or failing while the reader is still there - and deliberately not per streamed chunk; its settled key counts the transcript, so a whole turn that ran while the socket was down is not read back as nothing having happened. One phone drives several hosts, so the unit every screen is parameterized by is the saved host, not a token. `mobile/src/hosts.ts` owns the list, and two rules are load-bearing: an **origin identifies a host** (pairing one already saved re-pairs that entry and keeps the id its retained drafts are keyed on - so normalize a typed origin _before_ asking the host, since the field accepts a bare authority and a pasted deep link), and a token is **per host** (`revokedHostToken` drops exactly one into re-pairing; a `401` seen anywhere records it on the list, so a background host cannot linger holding a dead token). `host-status.ts` owns per-host reachability plus the retry schedule, and only the probe schedule's own outcomes may pace it - `notedHostOutcome` exists because the chat list's 3s poll would otherwise pin the backoff at its ceiling. `use-host-directory.ts` persists every mutation as it applies it and runs one timer chain per host; `App.tsx` keys every screen on the host id so switching tears the previous host's socket and poll down by remount, and puts the host switcher _ahead_ of the re-pair screen so a revoked token cannot trap the reader. Requests are addressed to a host explicitly (`hostApiUrl`/`hostSocketUrl`) because a relative path would always ask whoever served the page. Cross-origin is CORS rather than per-host bookmarks, argued in the plan doc; in code, `REMOTE_CORS_HEADERS` covers every API reply _including the `401`_ (without it a browser hands the client an opaque network error and a revoked token reads as an outage), the static bundle is served without them, an `OPTIONS` preflight is unauthenticated by necessity, and `*` is safe only because there is no ambient authority to grant - no cookies, no session, `Access-Control-Allow-Credentials` deliberately absent. WebSockets are not CORS-gated, but a browser does refuse `ws:` from an HTTPS page, which `hostBlockedByPageScheme` names rather than letting it read as an offline host. - The phone client installs itself, and installability is a property of the _origin_ rather than of the client: a service worker demands a secure context, Toucan deliberately owns no certificates, and `tailscale serve` in front of the plain-HTTP listener is the whole HTTPS story - the user-facing walkthrough, security model included, is `docs/mobile-companion-setup.md`. So "not installable" is the ordinary state and not a fault: `mobile/src/install-support.ts` skips with a named reason (`insecure-context` outranks `unsupported`, because an insecure context is _why_ a browser withholds the API, and the wrong one would misdiagnose the fix) and never rejects, so nothing on the loading path depends on a worker existing - while a genuine registration _failure_ is logged, since a failure and a skip send a reader to two different fixes. What the worker may cache is `mobile/src/service-worker-policy.ts` and nowhere else: the shell network-first, Vite's content-hashed `/assets/` cache-first (sound only because the URL changes whenever the bytes do), and pass-through for `/api/`, every non-`GET` and every _other_ origin - one phone drives several hosts, and a cached transcript, chat list or pairing verdict would be a stale workspace presented as live. `mobile/src/sw.ts` is a second, deliberately **unhashed** Vite entry (`sw.js`), because a worker is identified by its URL and a fingerprinted one would register as a brand new worker every build; it declares the handful of worker globals it uses locally rather than pulling in TypeScript's `WebWorker` lib, which redeclares half of `DOM` and so cannot share a program with the rest of `mobile/`. Its one cache is wiped of every other name on activate, so anything a later ticket caches separately has to be named there too. Manifest and icons are static files in `mobile/public/` regenerated by `npm run icon:mobile`, which reads the background colour off the manifest (its one authority) and rasterises the same logo the desktop icon comes from through the shared `scripts/rasterise-logo.mjs`. `tests/mobile-pwa-assets.test.ts` compares every declared `sizes` against the PNG's own IHDR, because Chrome withholds the install prompt _silently_ when they disagree. See also `tests/mobile-install-support.test.ts` and `tests/mobile-service-worker.test.ts`.

- The project sidebar has no `order` field and never will: array order _is_ display order. `projects` stays the single ordered list the remote projection maps, and `WorkspaceState.projectGroups` (optional, added without a version bump, like `attention` and `brainDumpPanel`) orders the groups; the sidebar renders groups first, each followed by the members of `projects` carrying its `groupId`, then the ungrouped ones. Groups are a **desktop-sidebar** affordance - they never reach the canvas, `RemoteProjectSummary`, or `mobile/`. All of the "where does this row land" maths lives in `src/renderer/src/project-order.ts` (no React), and a drag commits on `pointerup` only, because every write to `projects` re-serialises the whole workspace. Two load-time rules make an edited snapshot safe: a `groupId` naming no group is dropped and duplicate group ids are deduped in `parseWorkspaceState`, and a `color` failing `isProjectColor` (`src/shared/project-colors.ts`, the one home of the palette) is _substituted_ from the palette rather than refusing the snapshot - while `isWorkspaceState`, which is also the write-time guard, refuses to store anything but a lowercase `#rrggbb`. A colour is user-changeable now but still denormalised onto node data as `projectColor` at node creation, so `setProjectColor` in `App.tsx` must fan the new colour out across every chat/terminal/worktree node of that project in the same update or the canvas keeps the old tint until the next restore. See `tests/project-order.test.ts` and `tests/project-panel.dom.test.tsx`.

- Windows packaging is `electron-builder` with two x64 targets in `build.win.target`, `nsis` (per-user assisted installer, the prerequisite for in-place updates since a portable exe cannot replace itself) and `portable`; options and artifact names live in `package.json` and are locked by `tests/packaging.test.ts`, and the user-facing commands and SmartScreen step are in the README. Two rules are load-bearing: `package:win` must not name a target after `--win`, because a CLI target replaces the configured list rather than filtering it; and `artifactName` belongs per target (`build.nsis`, `build.portable`), never on `build.win`, or both targets collide on one file name. Everything the app needs at runtime ships through `out/**` plus the `asarUnpack` list - except the speech model: Vite copies a dev run's prepared model into `out/renderer/models`, and `build.files` excludes it (`!out/renderer/models/**`) because installed builds download it on first use (see the dictation note). The installer accepts NSIS silent switches (`/S /D=<dir>`, uninstaller `/S /currentuser`), which is how a build is smoke-tested without clicking through; when launching a packaged `Toucan.exe` from an agent shell, clear `ELECTRON_RUN_AS_NODE` first - agent hosts set it, and under it the exe runs as bare Node and dies with `bad option` (exit 9) rather than starting the app.

- Releasing is `npm run release -- patch|minor|major|<x.y.z>` (`scripts/release.mjs`): from a clean, up-to-date `main` it groups the commit subjects since the last `v*` tag into release notes (`scripts/release-notes.mjs`), shows them for confirmation (`--dry-run` stops there, `--yes` skips the prompt), bumps the version, commits, writes the notes into the annotated tag's body and runs `git push --follow-tags`. The workflow re-fetches the annotated tag - checkout flattens it to a commit pointer - and passes that body to `gh release create`, so the tag annotation is the only place release notes are authored. Do not use `npm version --dry-run` to preview a bump: it still rewrites `package.json` and the lockfile. The `v*` tag runs `.github/workflows/release.yml`, which verifies, builds, and publishes through `npm run publish:win` to the separate public repo named in `build.publish`, so downloads need no GitHub account while this repo stays private. Three settings are load-bearing and locked by `tests/release-workflow.test.ts`. `build.publish.releaseType` must stay `release`: electron-builder's GitHub publisher otherwise creates a _draft_, which a logged-out visitor cannot see, so the release silently fails its only purpose. `GH_TOKEN` must be the `RELEASES_REPO_TOKEN` secret, a fine-grained PAT with contents read/write on the releases repo alone - the workflow's own `GITHUB_TOKEN` is scoped to this repository and cannot write to another one. And `npm run check` runs before packaging, so a failed gate publishes nothing. The job sets `TOUCAN_SKIP_VOICE_MODEL=1` so the `prebuild` hook does not fetch a speech model the package excludes anyway; with the 291 MB model out of the installer a release runs well under the ~17 Windows-runner minutes it used to cost (Windows minutes bill at 2x), most of which was NSIS compressing the model. Release notes and the releases repo are public: nothing internal belongs in either. One more thing is load-bearing and easy to lose: the workflow claims the release with `gh release create` _before_ packaging. Each Windows target publishes independently and will create the release itself if none exists, so two creates race and the loser gets a 422 ("Published releases must have a valid tag") that aborts the remaining uploads - which is how v0.3.1 published its two installers but no `latest.yml`, leaving every updater check with no feed to read and, by design, nothing to show the user.

- Installed builds update themselves with `electron-updater`, which reads the same `build.publish` block electron-builder publishes through, so there is no second feed URL and no token (the releases repo is public). The sharp edges: only an NSIS install can be updated, and `PORTABLE_EXECUTABLE_DIR` - set by electron-builder inside a portable exe - is the only way to tell one apart at runtime, which is why `appUpdateSkipReason` reads it. `autoInstallOnAppQuit` is turned off deliberately: closing the window must never swap the binary under sessions Toucan is still hosting, so restarting is an explicit click and nothing else. That click calls `quitAndInstall(true, true)`, and both arguments are load-bearing: `isSilent` passes `/S` so the assisted installer skips its wizard and reuses the `InstallLocation` it recorded, and `isForceRunAfter` passes `--force-run`, which is the only condition under which a _silent assisted_ install starts the app again (`installSection.nsh`) - drop either and an update replays the first-install wizard or leaves the user at a closed window. And `electron-updater` verifies the SHA512 in `latest.yml` but skips signature verification while builds are unsigned - revisit once signing exists.

- Work is tracked as GitHub issues on this repo (`gh issue list`). `ready-for-agent` marks a ticket an agent may pick up now; `blocked` plus the issue body's "Blocked by" section gates a ticket on other issues; `backlog` defers it; `frontier-model` flags an architecture-sensitive ticket that should be implemented with the strongest available model rather than the default. When a ticket lands, flip any ticket it was the last blocker for from `blocked` to `ready-for-agent`. Feature plans that spawned a ticket set live under `docs/plans/` and each issue links its plan.

- Every commit message subject follows `type(affected-feature): ticket-number commit-message` - for example `feat(agent): 127 fan agent events out through a main-process broker`. `type` is a conventional-commit type (`feat`, `fix`, `chore`, `refactor`, `docs`, `test`, `build`, `ci`, `perf`), `affected-feature` names the area touched (`agent`, `mobile`, `worktree`, `remote`, ...), and `ticket-number` is the bare GitHub issue number the work belongs to - no `#`, which git would strip as a comment in an editor-composed message. When no issue covers the work, drop the number and keep the rest of the shape. Keep the message itself imperative, lowercase, no trailing period.
- Dictation is English-only on the desktop and says so in its label; the phone prefers its browser's own recognizer and only otherwise posts raw 16 kHz PCM to `POST /api/transcribe`, transcribed in main by the same model files. The model is not in the installer: `src/main/voice-model-store.ts` owns where it is (a dev run's prepared `src/renderer/public` directory, else `<userData>/models/...`) and the one shared download into userData on first use, with readiness meaning `streaming_config.json` is present - it is downloaded last and every file is renamed into place only at full size, so that one file proves the rest. A packaged renderer runs on `toucan://app`, never `file:`, and `src/main/app-protocol.ts` serves both the bundle and the model from it: Moonshine's threaded WASM needs `SharedArrayBuffer`, which only a cross-origin-isolated page gets, and a `file:` page's opaque origin can never be isolated no matter what headers are stamped on it - its pthread worker then fails its first `postMessage` inside a promise that never settles, which is a microphone stuck on "Preparing local speech model..." rather than an error. `file:` also cannot load the model at all: `fetch` and the Cache API both refuse a non-HTTP scheme. That second refusal is why `VoiceInput` fetches the model files itself (`voice-model-files.ts` on both sides, named and sized by the host) and hands the bytes to `Transcriber.load` instead of letting Moonshine's `AssetDownloader` do it - it caches every file through the Cache API. The scheme must be registered privileged (`standard`, `secure`, `supportFetchAPI`) before app ready, and the handler must set `Content-Type` itself, because a custom scheme has no server to label a module script or a streamed WASM compile. `src/shared/remote-voice.ts` is the one place the wire shape and the model directory name live, so `scripts/prepare-voice-model.mjs` must fetch the same architecture the renderer and main load. `src/main/remote/voice-engine.ts` is kept out of the test compile because the Moonshine package is ESM-only; the policy around it is tested through an injected engine. Measure accuracy with `npm run voice:wer -- <dir>` on the user's own recordings before changing models. See `docs/voice-input.md`.

- A project's branch is switched from the sidebar, never from a node. `ProjectBranchChip.tsx` in the project row shows the project checkout's branch and opens `ProjectRowMenu` straight onto its `branches` page (also reachable as "Switch branch…" from the right-click menu, which is the collapsed sidebar's only route). A node's own `CheckoutBranchChip` stays read-only because it names the checkout that node runs in - a worktree's for a worktree node - so a click there would read as "change this node's branch", which Toucan does not offer. `worktreeApi.listBranches` lists local branches only (`git branch --format` with `%(worktreepath)`, parsed by `parseLocalBranches` in `src/shared/git-branch.ts`); remote-only branches are deliberately absent because picking one creates a tracking branch, a different operation. `checkoutBranch` verifies `refs/heads/<name>` first for the same reason - a bare `git checkout <name>` would DWIM one from a remote. `describeBranchChoiceBlocker` is the one place that decides why an entry is greyed out: the current branch, a branch another worktree holds (git refuses those anyway), or any session mid-turn in the project checkout - refused outright, fail-closed, because a checkout swaps the files under an editing agent; worktree nodes do not count. App re-checks the working count at switch time, since a turn can start while the list is open. After Toucan's own switch `branchRevision` bumps so the rows re-read via `useCheckoutBranch(directory, revision)`; node chips simply catch up on their poll.
