# Project agent memory

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

- Every non-interactive `node:child_process` launch must apply `hiddenProcessOptions` from `src/main/background-process.ts`; it applies `windowsHide: true` last so no caller can accidentally re-enable transient Windows command windows. ACP adapters additionally inherit the preload policy in `agent-process.ts`, which covers provider CLIs they spawn themselves. The Codex rate-limit reader must resolve Windows npm shims to the matching native platform executable and launch it directly: hiding an intermediate `codex.js` wrapper does not prevent its inherited-stdio child from briefly surfacing a `PseudoConsoleWindow`. The `node-pty` terminal path is intentionally separate because it owns Toucan's interactive terminal surface. `tests/background-process.test.ts` inventories child-process importers to enforce this boundary, while `tests/codex-rate-limits.test.ts` locks down the native shim resolution. The same shim rule binds test launchers: current Node refuses to spawn a Windows `.cmd` without a shell (EINVAL), so `tests/architecture-dependencies.test.ts` runs dependency-cruiser's own JS entry under `process.execPath` instead of `node_modules/.bin` - and asserts a cruise report was actually produced, because a launcher that never ran otherwise presents itself as every rule being broken at once.
- A git worktree is a first-class workspace entity, not a per-node side effect. It is created explicitly (canvas context menu -> Worktree), persisted in `WorkspaceState.worktrees`, and rendered as its own `worktreeNode`; session nodes _reference_ one via `worktreeId`, so several nodes can share a worktree and closing a node never touches it. `TerminalNodeData.workingDirectory` (resolved in `restoreCanvasWorkspace`/`addSessionNode`) is the only value that may be sent as a `cwd` - `projectPath` is display-only now. A node whose worktree record vanished restores `detachedFromWorktree` and dormant rather than silently falling back to the project checkout. Teardown lives in `src/main/git-worktree.ts` and is evidence-gated: it proves shared git-common-dir and non-primary identity, then reports `WorktreeRemovalBlocker`s for dirty/untracked/stashed/unpublished work; missing evidence produces a blocker, never permission. `isForcibleBlocker` decides what a confirmation may override, and removal never deletes the branch, so forcing can only cost uncommitted and untracked files. `planWorktreeRemoval` in `src/renderer/src/worktree-removal.ts` folds attached-node count into that verdict. See `tests/git-worktree.test.ts` and `tests/worktree-rules.test.ts`.
- Attachment is what makes a node run in a worktree; an association is not attachment. `src/renderer/src/worktree-attachment.ts` owns both halves: `applyAttachedNodeCounts` derives every worktree's count from nodes carrying `worktreeId` (never from `activeWorktreeId`), and `adoptClaimedWorktrees` redeems the weak association discovery leaves behind. A worktree an agent made for itself is matched to its node by the claim `settle-worktree.mjs` writes when it sees `TOUCAN_NODE_ID` - so that variable must reach the adapter process itself via `agentProcessEnvironment` at the `buildAgentProcessLaunch` call, not only the `RunningAgent` record beside it. That claim is written after `git worktree add` and after the project's setup command, routinely later than the sweep that records the worktree, so `matchWorktreeClaims` reports claims for every worktree git lists (not only newly discovered ones) and `applyWorktreeClaims` links them against the whole canvas; a claim is a file agents append to and never prune, so a node is only ever linked or moved within its own project. Redeeming a claim restarts the session in the worktree, so it is Codex-only (Claude transcripts are directory-scoped) and only at a boundary with nothing in flight: `idle`, `result`, `dormant`, `exited` - never `working`, `starting`, `attention`, or `stalled`. `invokesWorktreeSkill` recognises both the unqualified `/implement-in-worktree` and the namespaced `/$<ns>:implement-in-worktree` slash completion actually inserts, matched by shape so no host's branding is baked in; recognising the prompt up front is the normal path, and claimed discovery is the fallback for a worktree the agent made anyway. See `tests/worktree-attachment.test.ts`, `tests/worktree-adoption.dom.test.tsx`, `tests/worktree-handoff.test.ts` and `tests/acp-session-manager-launch.test.ts`.
- Terminal identity has two layers: the workspace persists a durable `sessionId`, while `src/main/terminal-manager.ts` exclusively creates and owns the process `incarnationId` and liveness verdict. Every terminal IPC command and event carries both identities; never route by canvas node ID alone or infer exit from renderer/transport loss. Persisted live terminals hydrate as `unverifiable`; only the process owner's exit callback establishes `exited`.
- Plain-terminal history lives separately in `src/main/terminal-scrollback-store.ts`: one exact-incarnation snapshot per durable session, bounded to 512 KiB/seven days and removed with the canvas node. `TerminalNode` may render it while dormant, but it is display-only; never use retained output for liveness, input authorization, prompt detection, or any other operational state.
- `.terminal-node` (canvas chat nodes) is `overflow: hidden`, so any dropdown/menu anchored inside with CSS `position: absolute` clips at that ancestor's edge. `SelectorPicker` in `src/renderer/src/ChatNode.tsx` (the Provider/Model/Effort/Permissions pickers) instead portals its menu to `document.body` and positions it in JS against the trigger button's viewport rect via `computeNodePickerMenuPosition` in `src/renderer/src/node-picker-menu-position.ts`, clamped to stay fully on-screen. Follow the same portal pattern for any new floating menu inside these containers rather than CSS anchoring.
- The app has exactly one scrollbar. `:root` in `src/renderer/src/styles.css` declares `scrollbar-color: #3b4553 transparent` and `scrollbar-width: thin`; both properties inherit, so every scroll container - panels, dialogs, menus, the chat transcript, file nodes, composer, terminal viewport - already has the chat-node scrollbar and must never redeclare one. A new scrollable surface needs no scrollbar styling at all, and a surface showing the platform default scrollbar means something above it overrode the inherited value rather than that it forgot to opt in. `tests/scrollbar-styling.test.ts` locks both halves: the root declaration and the absence of any per-component redeclaration.
- `promptWhenIdle` in `src/main/acp-session-manager.ts` uses the adapters' advertised `_session/steering` extension while a turn is working, so accepted follow-ups are injected exactly once and the adapter observes them at its next safe boundary without replaying or cancelling the turn; a single non-yielding tool can delay that boundary. Adapters without steering fall back to the non-expiring FIFO `PromptWakeGate` in `src/main/prompt-wake-gate.ts`, drained after turn completion/Stop.
- `withStallGuard`/`StallTimeoutError` (`src/shared/stall-guard.ts`) is the shared "bound a promise that might never settle" primitive for operations that genuinely have a deadline, such as `VoiceInput` model load/start and the Codex account-rate-limit read. Never wrap a whole ACP `session/prompt` turn in it: a turn spans every tool call and has no wall-clock deadline, so elapsed time cannot distinguish healthy long-running work from a wedge. `settleAgentTurn` in `src/main/acp-session-manager.ts` waits for the provider's real completion/rejection or explicit cancellation; manual Stop and the renderer's non-destructive inactivity indicator are the recovery paths.
- `createWorkspaceStore` in `src/main/workspace-store.ts` owns all workspace-canvas persistence. `save()` serializes concurrent calls through an internal promise queue, validates the incoming state, writes it to a temp file via the shared `writeFileDurably` helper (fsynced, and unlinked again on any write failure), promotes the current (still-valid) primary snapshot to a single bounded `<path>.backup` recovery copy, then atomically renames the temp file onto the primary (also unlinking the temp file if that rename choreography fails) — so a crash or a failed save at any point leaves either the untouched old primary+backup or a fully-written new primary, never a torn file or a leaked temp file. `load()` returns a `WorkspaceLoadResult` (`state`, `recovered`, `unrecoverable`): it falls back to the backup and self-heals the primary when the primary is missing/corrupt (`recovered: true`, surfaced by `App.tsx`'s "Recovered from backup" indicator), and when neither primary nor backup validates but at least one of those files exists on disk, it reports `unrecoverable: true` with `state: null` instead of the fresh-install case (`unrecoverable: false`) — callers must never silently seed and autosave a fresh default over `unrecoverable: true`, since that would permanently destroy the last damaged-but-potentially-recoverable copy. `App.tsx` enforces this: on `unrecoverable`, it shows a non-dismissable warning dialog and only seeds a fresh workspace after the user explicitly acknowledges it. Both primary and backup reads go through `parseWorkspaceState`, so schema migrations apply uniformly to either. See `tests/workspace-store.test.ts` for the interruption/corruption/concurrency/unrecoverable scenarios this guarantees.
- Both ACP adapters replay a resumed session as `session/update` notifications during `session/load`. `src/main/acp-session-manager.ts` buffers that finite stream into `AgentCreateResult.replay`, and `useAgentConversation` folds it through the live event handler; keep replay off the separate `agent:event` IPC channel, where renderer startup can lose it. That folding is not the hook's: `foldAgentEvent`/`applyAgentCreateResult` in `src/shared/agent-transcript.ts` is the pure, runtime-neutral reducer every host (renderer today; main/remote later) runs over the same `AgentEvent` stream to derive an identical transcript, and the hook is a thin wrapper owning only renderer-local delivery state (draft, outbox, optimistic-send echo dedupe) and IPC - new transcript-shaped state belongs in the reducer, not in the hook (`tests/agent-transcript.test.ts`). Codex distinguishes commentary from final text only through replay-stable `_meta.codex.phase`, preserved as `AgentEvent.presentation`. For unphased assistant text (including Claude), `src/shared/assistant-presentation.ts` presents it as provisional progress and promotes only the last message of each completed live or replayed turn to final. `isFinalAssistantMessage` is the shared gate for final-only title, decision, and result-attention behavior; progress remains available in transcript history and worktree handoffs even when Focus hides it. Claude reasoning remains the separate `agent_thought_chunk` path. `isInternalNotificationText` filters Claude's synthetic supervision injections where Toucan consumes `session/update`. See `tests/assistant-presentation.test.ts`, `tests/restored-chat-transcript.dom.test.tsx`, and `tests/acp-session-manager-replay.test.ts`. Live events are never sender-bound: `acp-session-manager.ts` publishes every `AgentEvent` to the `AgentEventBroker` (`src/main/agent-event-broker.ts`, injected at the composition root), which folds each event into a per-session main-process transcript snapshot and fans it out - the creating renderer is only subscriber #1, and `subscribe` returns snapshot + gap-free live tail atomically for late joiners (the remote server's join contract). Replay is `fold`ed into the snapshot but never fanned out, `stop` closes the channel unconditionally so the renderer's kill-then-recreate cycle cannot stack owner subscriptions, and answering an approval publishes `approval_resolved` so every subscriber retires the same pending card. See `tests/agent-event-broker.test.ts` and `tests/acp-session-manager-broker.test.ts`.
- ACP auth-required detection has one home, `isAuthRequired` in `src/main/acp-session-manager.ts`, feeding both `promptFailure` (mid-conversation) and `openSession`'s catch (session creation/resume) so every auth failure reaches the same `{ type: 'auth', methods }` sign-in UI.
- There are two test runners: `tests/**/*.test.ts` (compiled by `tsc -p tsconfig.test.json`, run with `node --test`) covers non-UI logic and has no DOM; `tests/**/*.dom.test.tsx` (Vitest + jsdom + `@testing-library/react`, config in `vitest.config.ts`, setup in `tests/dom/setup.ts`) actually renders renderer components/hooks.
- Transcript markdown lives in `src/renderer/src/MarkdownMessage.tsx` (GFM via `remark-gfm`), and it re-renders on every streaming chunk. Syntax highlighting therefore must not be a rehype plugin — that would re-tokenize every code block in the message per chunk. `pre` is replaced by a `React.memo`'d `CodeBlock` keyed on its own text, so only the block still streaming is re-highlighted; keep that shape for any future per-block work. Markdown links (including GFM autolinks) go through `terminalApi.openExternal` → the `shell:open-external` handler in `src/main/index.ts`, which forwards http/https only; a plain `<a>` would navigate the app window away. See `tests/chat-markdown.dom.test.tsx`.
- Past conversations are browsable and resumable independently of any node: `src/main/conversation-history.ts` enumerates both providers' transcripts for a set of working directories (a project checkout plus its worktrees) and `ConversationHistoryDialog.tsx` (canvas context menu -> History) opens the picked one as a node with `launchMode: 'resume'`. Enumeration is deliberately two-phase - candidates cost a directory entry plus, for Codex, one head read cached by path (a `session_meta` line never changes), and only the requested page's transcripts are read in full - so a project with hundreds of transcripts stays responsive. Claude project folders are matched case-insensitively against `encodeClaudeProjectDirectory` because the same checkout reaches the CLI under either drive-letter case; Codex subagent rollouts (`thread_source: 'subagent'`) are excluded because they are not resumable conversations. A row whose transcript has since been deleted is reported in place via `conversationApi.exists` rather than opening a resume that cannot find its conversation. `@agentclientprotocol/codex-acp` is held at an exact version in `package.json` rather than a range, because what an ACP adapter does to a resume is not something the suite can reach: it needs a live Codex process replaying a transcript. Upgrade it deliberately, and confirm afterwards that a Codex conversation opened from History still loads its content - Codex `0.147.0` once broke exactly that, rejecting history opened while another client owned the thread as `already has an active writer`. Verified working on codex-acp `1.8.0`/Codex `0.152.1` (2026-09-05). See `tests/conversation-history.test.ts` and `tests/conversation-history-dialog.dom.test.tsx`.
- Conversation titles are local and durable: `deriveConversationTitle` in `src/shared/conversation-title.ts` derives one stable title from enough dialogue without a model call (zero tokens/account budget), while `src/main/conversation-title-store.ts` keeps provider/session-keyed metadata outside provider-owned transcripts. Generated writes are first-write-wins; manual writes may rename repeatedly and always outrank later generation. `WorkspaceTerminalNode.titleSource` preserves the node header/sidebar identity, and history consults the same durable metadata. Keep title normalization shared and never rewrite provider transcript files. See `tests/conversation-title.test.ts` and `tests/conversation-title-store.test.ts`.
- The composer is a prompt editor, and its decisions live in small pure modules the rendered `Composer` in `src/renderer/src/ChatNode.tsx` only wires together: `composer-keys.ts` (one function decides send vs newline vs history-walk from the workspace-wide `ComposerSendKey`), `prompt-history.ts` (session prompt ring, walked with the arrows from an empty composer), `composer-autosize.ts` (growth bounds), `slash-command-completion.ts` (when a `/` token is a command, how the list narrows, what accepting inserts and where the caret lands), and `prompt-outbox.ts`. `file-mention-completion.ts` is the same shape for `@`: how the index narrows and ranks, and what accepting inserts. What counts as a token at all is one rule both share, `tokenOpeningWord` in `completion-token.ts`: a sigil starts a token only where a word starts - the draft's start or after whitespace - so `src/main` and `morgan@example.com` stay prose while `now run /code-review` opens the list. Deliberately whitespace and nothing else (`(/rev` is left alone), and deliberately _not_ anchored to the line start: agents honour `/<name>` as an invocation anywhere in a prompt, so a picker that only opened a line would refuse exactly the mid-prompt invocations that work (issue #140). One consequence worth knowing: `invokesWorktreeSkill` in `src/shared/worktree-handoff.ts` still recognises the skill only on the first line by design, so a mid-prompt `/implement-in-worktree` completes but routes through claimed discovery rather than up-front recognition. Both pickers render through one `CompletionMenu` in `ChatNode.tsx` and only one is ever open - the shared rule makes the two mutually exclusive, since a word start is either a `/` or an `@`. The slash list is never hardcoded: it is whatever the session advertised through ACP's `available_commands_update`, normalized by `simplifyAvailableCommands` in `src/main/acp-session-manager.ts` and cached there so reopening an agent isn't left blank. The outbox is the load-bearing one: a follow-up submitted while a turn is working is held _in the renderer_, never handed to `promptWhenIdle`, because a prompt that has crossed into the adapter (steered into the running turn, or parked in the main-process `PromptWakeGate`) can no longer be taken back — that hold is what makes Edit/Withdraw mean anything, and "Send now" is the explicit opt-in back into steering. Decision answers and `sendMessage` deliberately bypass the outbox and still steer immediately, since the agent is actively waiting on them. The outbox drains one prompt per idle turn. Drafts belong to the node (`WorkspaceTerminalNode.draft`), not the ACP session, so they outlive resize, collapse and reload; the Composer debounces them upward through `onDraftChange`. Toucan has no editor, so "open/recent" is the set of files the agent has already read or written this conversation (activity `locations`) - that is the picker's top band and the only signal the composer gives about what the agent can already see. The @ picker's files come from `src/main/workspace-file-index.ts`, which lists one working directory through `git ls-files --cached --others --exclude-standard` (so `.gitignore` is honoured by construction), falls back to a bounded walk where git cannot answer, and caches per root - a keystroke must never cost a directory walk, and the picker states in the UI whichever exclusion is in force. Every read is keyed on the node's resolved `workingDirectory`, never `projectPath`, because the inserted reference is resolved against it. Accepting inserts the root-relative path as plain text rather than an ACP `resource_link`: both installed adapters flatten a resource link back into text before the model sees it, so the block would buy nothing and cost the composer's plain-text draft, prompt history and echo matching. The composer's wheel handling is deliberately conditional rather than a static React Flow `nowheel`: `composerConsumesWheel` in `composer-autosize.ts` stops the event only while the grown box still has travel in that direction, so a long draft scrolls instead of zooming the canvas while a resting composer still lets the canvas zoom. It must stay a native listener bound to the textarea - d3-zoom listens on the pane between the composer and React's delegated root, so a React `onWheel` would stop propagation too late to prevent the zoom. See `tests/file-mention-completion.test.ts`, `tests/workspace-file-index.test.ts`, `tests/composer-file-mentions.dom.test.tsx`, `tests/composer-prompt-editor.dom.test.tsx`, `tests/composer-queue-while-busy.dom.test.tsx` and `tests/composer-wheel.dom.test.tsx`.
- Tool activity has one home: the transcript. The shared reducer records first-seen message/activity/turn-outcome order in `transcript`; `ChatView` interleaves `ActivityCard`s, reasoning blocks, and visible failed/cancelled turn boundaries with dialogue, while per-node `focusMode` hides activity, reasoning, plans, and transient detail without hiding terminal outcomes. Reasoning is _not_ one card per thought message: `mergeReasoningEntries` in `src/renderer/src/reasoning-blocks.ts` is the desktop's one place that decides where one deliberation ends, and it decides it in transcript order - a run of adjacent thought chunks is one block, and an intervening tool call or piece of prose is what separates two; the mobile client (barred from renderer imports) applies the same adjacency rule for its collapsed indicator in `mobile/src/chat-view.ts`, so a boundary change must land in both. A block is identified by its first chunk, so it keeps its React key while it grows; expansion therefore lives in `ChatView` rather than the card, because `focusMode` unmounts these cards and local state would forget a block the reader opened. Size is a deterministic estimate from the merged text, never elapsed time: `session/load` replay re-delivers a whole conversation's thoughts in one burst, so a duration would read as milliseconds for a deliberation that took minutes. Only the trailing block of a `working` session is `streaming`, which is what the live tail-line preview and pulse are gated on. See `tests/reasoning-blocks.test.ts` and `tests/chat-reasoning-blocks.dom.test.tsx`. Provider replay cannot reproduce Toucan-side failures, so the newest bounded `WorkspaceTerminalNode.turnOutcomes` are persisted with the node. `WorkspaceTerminalNode.focusMode` persists the view choice and loading migrates legacy `worklogCollapsed`; the right-side rail no longer exists. Every tool call uses the shared `ActivityCard` shell in `ChatNode.tsx`; add families only through `toolCardFamilies` in `tool-card-families.tsx`. `mergeActivity` supplies client-side timing, bodies are line-clamped before the DOM, and a collapsed card reopens if it later fails. Purpose-built cards depend on `activityFromUpdate` preserving tool name, `rawInput`, `rawOutput`, and diffs; claude-agent-acp reports its name through `_meta.claudeCode.toolName`, and a `Write` is `kind: 'edit'` with `oldText: null`, so payload outranks diff shape when identifying it. Paths shorten through `WorkspaceRootsContext`. See `tests/chat-focus-view.dom.test.tsx`, `tests/tool-card-shell.dom.test.tsx`, and `tests/file-operation-cards.dom.test.tsx`.
- Tool calls arrive in one flat feed even when they were not one agent's work, and the two adapters report delegation in two different shapes. claude-agent-acp _nests_: a subagent's own tool calls arrive as ordinary top-level `tool_call` notifications stamped with `_meta.claudeCode.parentToolUseId` (from the SDK's `parent_tool_use_id`), and the spawning `Task`/`Agent` call is stamped `claudeCode.subagent`. codex-acp _never_ nests and forwards none of a subagent's tool calls: it reports each interaction with one (`started`/`interacted`/`interrupted`) as its own top-level call under `_meta.codex.subagent`, sharing one `rawInput.agentThreadId` - so that thread id is the only link there is, and those interactions _are_ the only progress Codex reports. `delegationOf` in `src/shared/agent-activity.ts` is the only reader of the `_meta`, surfacing `parentToolCallId`/`subagent` on `AgentActivity`; `indexSubagentActivities` owns both links, and `worklog-activities.ts` decides whether a call renders inside its delegation rather than as a separate transcript card. Without all of that, a delegated Read reads as the main agent's and the `Task` card sits at "running" for minutes. Only subagent text/thinking is gated behind the adapter's `subagent-transcript` client capability, which Toucan deliberately does not claim - it would route a subagent's prose into the top-level message feed. Todo/task writes are the mirror case: both adapters translate `TodoWrite`/`TaskCreate`/`TaskUpdate` into ACP `plan` notifications and _suppress_ the tool call, so the current plan's inline card is normally the only place a plan appears; the exception is a plan write that needed approval, which is surfaced as a real tool call, and `isPlanUpdateFoldedIntoRail` prevents that from becoming a second top-level card. See `tests/task-plan-skill-mcp-cards.test.ts` and `tests/task-plan-skill-mcp-cards.dom.test.tsx`. One ordering constraint the registry depends on: every family's recognizer flattens a tool name to its bare identity (`normalizeToolName` in `tool-input.ts`), so `mcp__tracker__task` and `mcp__docs__grep` collide with built-ins - the MCP family is registered first for exactly that reason, and the delegation/plan/skill recognizers each re-check it.
- What a conversation has consumed is shown per node in the chat's status-bar row, and every decision behind it - the 75%/90% bands, token and cost formatting, clamping, which account window is the one about to bite - is a pure function in `src/renderer/src/session-usage.ts`; `SessionUsageBar.tsx` is markup and does no display maths of its own (a readout hands it a `displayPercent`, already clamped and rounded), and it takes the finished readout rather than raw usage so `ChatNode` knows whether to reserve the grid row at all. Context and cost come from ACP's `usage_update`, forwarded structured, never pre-formatted, as the `usage` `AgentEvent`. The adapters report those fields independently - Claude sends `cost` (USD) only once a turn has produced tokens, Codex sends none at all, and either may report tokens before it knows the window - so an update is folded in by `mergeSessionUsage` as a _patch_: overwriting wholesale would blank a cost or gauge the reader was already shown. For the same reason a token count with no window still renders, just not as a fraction. Account rate limits are per provider, not per session: `App` polls `usageApi.rateLimits()` once and publishes it through `ProviderRateLimitsContext` (`provider-rate-limits.ts`), because each node polling would multiply a read that boots a CLI process. Codex usage comes from app-server's live `account/rateLimits/read` snapshot, bounded by `withStallGuard`, with the newest rollout transcript only as a compatibility fallback; Windows npm `.cmd` shims must resolve to Codex's JS entry point so timeout cleanup cannot strand a child app-server. Both the header's account chips and the node's gauges render `.usage-window` with a `data-level`, so the bands are one CSS rule set (`--usage-warning`/`--usage-critical`) and one window never reads as two different states. See `tests/codex-rate-limits.test.ts`, `tests/session-usage.test.ts` and `tests/session-usage-bar.dom.test.tsx`.
- Assistant decision messages (labeled multiple-choice questions) are recognized by `src/renderer/src/decision-message.ts` from plain text. `src/renderer/src/pending-decisions.ts` owns stable task/key identity, replay/open-wake dedupe, deterministic multi-decision ordering, and resolution folding.
- Provider-native user questions are ACP form elicitations, not transcript messages: Toucan advertises `elicitation.form`, `acp-session-manager.ts` normalizes select/multi-select/text/number/boolean fields into `AgentDecisionRequest`, and `StructuredDecisionPanel` renders one question at a time with retained tabbed answers before returning one typed response. Optional questions may remain unanswered; concurrent requests stay FIFO so one cannot overwrite another. Both installed adapters bridge their native tools (`request_user_input` / `AskUserQuestion`) through this path. While either a structured request or legacy prose decision is pending, the ordinary composer is hidden so free text cannot bypass the response channel. Keep `decision-message.ts` conservative as a legacy fallback; numbered bold questions are questions, not option buttons. See `tests/acp-session-manager-decisions.test.ts` and `tests/chat-decision-messages.dom.test.tsx`.
- Unread is one durable, persisted record set, not a per-render flag; `TerminalNodeStatus` (`working`/`stalled`/`starting`) stays the _live_ read on a session and no longer decides what needs attention. `src/shared/attention.ts` is the only place that decides what an approval, sign-in request, finished turn, or failure means; records persist as `WorkspaceState.attention` and are pruned to live node ids in `parseWorkspaceState`. Plain terminal output is progress and must never raise attention; a generic PTY stream cannot reliably distinguish an input prompt from ordinary output, so terminals only raise automatically for explicit failures. Nodes never own attention: they report one `AttentionAction` (raise/read/unread/resolve) through `onAttention`, `App.tsx` supplies only the clock and calls `applyAttentionAction`, and every count - node badge, sidebar row, project avatar, header chip - plus the node's own dot (`dominantUnreadKind` → `data.unreadKind`) is a selector over that same set, so they cannot disagree. **Read is sticky per condition**: re-recording a condition the user already read never re-raises it, which is what makes ACP session replay safe - so a condition that genuinely recurs must present a new key (approvals key on the ACP request id; turn failures on their turn id; results and non-turn errors on a digest of their text via `attentionTextKey`). **Reading clears only `READ_ON_VIEW_KINDS`** (result/failure/output, with output retained for persisted compatibility): looking at a pending approval or sign-in request is not answering it, so those are retired by `resolve` alone and survive both a glance and a restart. See `tests/attention.test.ts`, `tests/attention-surfaces.dom.test.tsx`, and `tests/terminal-output-attention.dom.test.tsx`.
- Recently closed session nodes are a bounded, persisted LIFO stack (`WorkspaceState.recentlyClosedNodes`), populated only through `App.tsx`'s React Flow removal wrapper. `Ctrl+Shift+T` is consumed only when `closedSessionKeyAction` can reopen an entry; `reopenClosedSession` in `canvas-workspace.ts` rebuilds runtime callbacks, resumes the saved conversation/session at its original position, and preserves the detached/dormant safety rule when a referenced worktree has vanished. Keep future session-node close paths routed through that wrapper. See `tests/canvas-workspace.test.ts` and `tests/workspace-store.test.ts`.

- The brain-dump library is a _docked_ panel, and three details keep it that way. It is a sibling of `.canvas-region` inside `.workspace-shell`, so it consumes layout width and React Flow simply re-measures - never an overlay, and never a remount that would reset the viewport. It is mounted lazily on first open and thereafter only `hidden`, which is what preserves collection, selection, search, scroll, and an unsent draft across a close; scroll offsets are additionally remembered in a ref because `display: none` drops them. Every width that reaches the DOM has been through `clampBrainDumpPanelWidth` in `src/renderer/src/brain-dump-panel-layout.ts` - on restore, on window resize, and on drag - so a width saved on a bigger monitor can never squeeze the canvas out. Panel state (open/width/draft/project/provider) persists as the optional `WorkspaceState.brainDumpPanel`; absent means "closed", so older snapshots migrate by doing nothing. `[[slug]]` is not Markdown: `brain-dump-links.ts` rewrites references into links on the private `toucan-topic:` scheme _outside_ code spans and fences, and the reader passes `urlTransform={keepHref}` because react-markdown would otherwise strip `file:` and private schemes - `classifyBrainDumpLink` is the real gate, and anything it does not recognize renders as inert text with no `href`. The reader's `a` component is built once and reads live values through refs on purpose: rebuilding it when a reference resolves would unmount every rendered link, and a link clicked in that instant would be a detached node with no handler, which in Electron means the window navigates away. Archived topics are immutable implementation-boundary snapshots: the UI/API only archive and reassign, and `.agents/skills/brain-dump/SKILL.md` turns later related material into a distinctly named active follow-up with an explicit `New work` section and a `[[slug]]` link back. Which project a topic belongs under is the capture skill's guess, so it is correctable: `assignProject` in `src/main/brain-dump-library.ts` rewrites the `project` frontmatter of an _active_ topic in place (a replacing rename, unlike `move`'s hard-link promotion between collections) and refuses an archived one; it deliberately does not touch `updated`, because filing is metadata rather than new material. The chip that reports the project is the control that changes it - `BrainDumpProjectPicker` in the reader, offering only registered projects plus Unassigned so a pick can never write an unresolvable path, and read-only `BrainDumpProjectChip` everywhere a topic cannot be reassigned. There is exactly one picker, in the reader: list rows are listbox `option`s, so a row's chip must never become a control of its own - it selects the row and raises the panel's `projectPicker` nonce, which the reader's picker consumes as `openSignal` and retires on open. Its menu portals to `<body>` through the shared `usePortalMenuPosition` (`use-portal-menu-position.ts`, also behind `ChatNode`'s pickers), since the panel's columns clip overflow. Both ends of the write compare paths through `brainDumpPathIdentity`, never raw string equality. `src/main/brain-dump-watcher.ts` watches and debounces Markdown changes per disk collection; its preload event makes `useBrainDumpLibrary` silently re-read every already-loaded collection, while unopened collections stay lazy. A background capture outlives the review tray, so its progress, Cancel, and failure recovery live in `BrainDumpCaptureStatus` at panel level, never inside `BrainDumpCapture` - closing the tray must not be able to strand a running job. A completed capture is believed only after `list('active')` is re-read from disk; the skill's summary is announcement text, never state, and the provider becomes the remembered preference only at that point. Watcher refreshes must yield to this capture-owned read or they can consume the before/after diff and prevent selection of the filed topic. See `tests/brain-dump-panel.dom.test.tsx`, `tests/brain-dump-reader.dom.test.tsx`, `tests/brain-dump-capture.dom.test.tsx`, `tests/brain-dump-watcher.test.ts`, and `tests/brain-dump-project-picker.dom.test.tsx`.

- Tickets are Markdown files in the checkout, and the files are the truth. `src/shared/tickets.ts` decides what a conforming file is and `.agents/skills/tickets/SKILL.md` is the same convention written for agents: change both together. Frontmatter parsing is shared with brain dumps through `src/shared/frontmatter.ts`. Closing a ticket is `status: done`; getting rid of one is deleting the file - no archive folder, no trash, git history is the backup.

- The ticket board (`src/renderer/src/TicketBoardPanel.tsx`) is a projection, never a copy: a dropped or deleted card changes on screen only after the write is awaited and the sources re-listed. It is a second docked panel built on the brain-dump panel's rules (sibling of `.canvas-region`, lazily mounted then `hidden`, optional `WorkspaceState.ticketBoardPanel`), and everything above `TicketSource` in `src/shared/ticket-source.ts` knows only cards, so a new tracker is another source and nothing else. Capabilities are what a source declares: `setStatus` is what lets a column accept a drop, `remove` what puts Delete on a card, `removalNote` where the git-checkout wording comes from. The watcher never creates a tickets folder to watch it, and `ticket-directory.ts` ignores a `ticketsDirectory` that leaves the checkout. Session chips on cards come from files a chat node actually wrote (`ticket-activity.ts`), matched by path identity, never inferred from a status. The board is three panes - states, the selected state's tickets, the selected ticket's body - and `ticket-board-panes.ts` owns every decision behind them: a state row is only ever *fallen back to*, never committed, because the very first render happens before any source has answered; the open ticket is keyed by `ticketCardKey`, so a drop that moves it drags the state selection along instead of closing the detail; and a panel too narrow for three panes shows the detail *instead of* the list, which is why the detail owes a back affordance in that mode only. The drop target is a state row, and Left/Right mean "another pane" everywhere except on a card's grip, where they still mean "another state" - the grip stops the press from being read twice. The module docblocks carry the rest; tests are `tests/ticket-*.test.ts`, `tests/ticket-board-panel.dom.test.tsx` and `tests/ticket-session-cards.dom.test.tsx`.

- A file node (`src/renderer/src/FileNode.tsx`, type `fileNode`, persisted as the optional `WorkspaceState.files`) is layout, not a session: a node whose file has gone keeps its place and reports "not on disk" itself, only a vanished project drops it, and closing one is filtered out of `rememberClosedSessionNodes` so it neither becomes a Ctrl+Shift+T target nor wipes the stack the way a worktree close does. Every file node is built through `createFileCanvasNode` in `canvas-workspace.ts`, and its Rendered/Raw choice is node data (`onViewModeChange`), never component state, so it survives a restart. The renderer never reads or writes bytes: `src/main/file-view.ts` is the only reader and writer and it **fails closed** - a path is readable or writable only when its _real_ path (links resolved) lies inside a registered project checkout or worktree, with the roots re-read from the snapshot per call; oversize reads are `truncated` rather than refused. Changes are watched through the file's _directory_, because editors and agents rename a temporary over the file and a watch on the inode misses that; holds are counted per window and path, so two nodes on one file survive either closing, and an `unwatch` that lands while the roots are still being checked still wins. The raw view is a CodeMirror 6 editor (`CodeEditor.tsx`, grammar picked by `@codemirror/language-data` from the file name, tokens themed through `classHighlighter`'s `tok-*` classes in `styles.css`; the transcript's code blocks still use lowlight); a truncated or binary read is read-only because saving a partial view would write it back as the whole file. Editing keeps **disk as the truth**: the draft and the `mtime` it was based on live in the pure `FileEditState` reducers in `file-node.ts`, a save hands that `baseMtime` to `write`, which refuses a changed file as `conflict` after replacing atomically through a temporary, and a change the watcher reports under a draft (or a conflict verdict from a save) becomes a banner offering Reload or Keep - the draft is never replaced and the file is never overwritten silently. The node's own save is recognised by the `mtime` the write returned, so the watcher event it causes is not a conflict. Unsaved drafts are component state and do not survive a restart. Files arrive two ways, both through `addFileNode` in `App.tsx`: the context menu's `FilePickerDialog` (the composer's `@` index, files only) and "Open" on a transcript file card, offered only where `OpenFileContext` is provided and filed under the deepest checkout or worktree containing the path (`projectOwningPath`). CodeMirror mounts under jsdom only with the range stubs in `tests/dom/codemirror-jsdom.ts`, loaded by the Vitest setup. See `tests/file-view.test.ts`, `tests/file-view-ipc.test.ts`, `tests/file-node.test.ts`, `tests/file-node.dom.test.tsx` and `tests/file-open-entry-points.dom.test.tsx`.

- Fit mode is workspace state, not node state: `useNodeFit` (`src/renderer/src/use-node-fit.ts`) owns the single fitted node and its session-local restore geometry, and the decisions are pure functions in `node-fit.ts` (`requestNodeFit` restores whichever node is already fitted before fitting the next, `reflowFittedNode` recomputes geometry for a changed canvas, `exitsNodeFitMode` distinguishes a user drag/resize from React Flow's own measurement). The usable canvas is _observed_, not derived: one `ResizeObserver` on `.canvas-region` covers application resize, sidebar collapse, and the docked brain-dump panel, because all three are layout siblings - so nothing reads window size or panel state, and reflow only ever reads the viewport, never writes it. The node's `fittedToCanvas` data flag is presentation for the header action; persistence and recently-closed capture must go through `nodeBeforeTemporaryFit`, which keys on the fitted node's id so a fitted node is never saved filling the screen. See `tests/node-fit.test.ts`, `tests/node-fit-mode.dom.test.tsx` and `tests/node-fit-action.dom.test.tsx`.

- Remote access (`src/main/remote/`) is Toucan's only network surface and it is off until the user enables it. Two rules keep it honest. The pairing token is the whole authorization story - every `/api` route checks it with `pairingTokenMatches` (constant time), it is only ever read from an `Authorization: Bearer` header, and `resolveRemoteRoute` decides authorization per _route_ so a new endpoint cannot forget the gate; the static client bundle is deliberately public, because a phone cannot set a header on the navigation that loads the pairing screen. And the canvas stays the one authority on what a phone lists: `useRemoteAccess` publishes a `RemoteWorkspaceProjection` (derived by `deriveRemoteWorkspaceProjection` in `src/shared/remote-access.ts`) and the host serves the latest one - never deriving its own view of the workspace, and never stamping the clock in the renderer, since a timestamp there would defeat the dedupe that stops a node drag from publishing per frame. Reading a chat live is `WS /api/chats/:id` (`ws`, `noServer`): the upgrade runs the same token gate first - also accepting the token from the `Sec-WebSocket-Protocol` bearer entry defined in `src/shared/remote-chat.ts`, because a browser cannot set a header on an upgrade - then only admits ids the published projection lists, and each socket is one broker subscription delivering a `{snapshot}` frame then `{event}` frames (`AgentEvent` verbatim, no DTO layer). A snapshot frame is a full resync the client applies wholesale, which is what makes reconnect and mid-stream replay repair duplicate- and gap-free; the broker's `closed`/`resync` subscription hooks exist for exactly this subscriber, and regenerating the token or stopping the listener closes every live socket rather than stranding it. Writing back goes over the same socket and through one narrow seam, `RemoteChatSessionOperations`: a `prompt` frame is answered with a `prompt_result` for its `requestId`, always - accepted, or refused with the session manager's own reason - because a send with no verdict is the one thing a phone composer cannot recover from. Two rules make that honest. The phone's policy is **blocked with a hint, never queued and never steered**: a working session is not a send target, and the host independently refuses one, so a race surfaces as a visible error instead of an accidental nudge into a turn in flight. And the host answers at _acceptance_, not at turn end, which is why remote sends use `AcpSessionManager.startPrompt` rather than `prompt` (whose promise settles when the whole turn does, and would read a failed turn as a failed send); the turn reports itself through events like everything else. The user message itself is authored by main, not by either UI and not by the provider: neither adapter echoes a live prompt back as a `user_message_chunk` (only `session/load` replay carries user chunks, and the manager drops any live one so no client needs a dedupe of its own), so `beginTurn` - and the steering path of `promptWhenIdle` - publishes one `role: 'user'` message with a fresh `messageId` at the moment a prompt is accepted, ahead of `status: 'working'`, whatever the prompt's origin. Its text is `promptText` (the prompt's text blocks only; images stay desktop-local render state, so an image-only prompt publishes nothing). The phone therefore renders no optimistic bubble and folds that event like any other host; the desktop keeps its optimistic bubble, which carries UI metadata the event cannot, and `pendingSentRef` in `use-agent-conversation.ts` consumes the host's event as that bubble's echo by matching the composed prompt text. The phone client lives in `mobile/` (its own Vite build into `out/mobile`, run by `npm run build:mobile` after `electron-vite build`) and imports `src/shared` types only; its connection, composer and rendering decisions are the pure `mobile/src/chat-connection.ts` (which owns the draft, so "what happens to what you typed when a send fails" is testable data) and `mobile/src/chat-view.ts`, folding the tail through the same shared reducer as every other host. `promptTextProblem` in `remote-chat.ts` is run by both ends, so the composer greys its button out in the exact words the host would have refused with, and an unsent draft is retained per chat in the phone's own `localStorage` - retention, never drafts sync - because a revoked token unmounts the chat screen on its way back to pairing and the typed text has to survive that. Answering a pending request travels the same socket as its own message type - `approval` and `decision` frames, answered with an `answer_result` - and never as free text: while a request stands the phone hides the composer entirely (`composerHidden`/`pendingRequest` in `chat-connection.ts`, one decision at a time with an approval outranking a queued question set, mirroring the desktop), so nothing can bypass the channel the agent is parked on. The race between two clients is decided in one place, and it is not the UI: `resolveApproval`/`resolveElicitation` key acceptance on the session's pending-request map, so whichever answer arrives first removes the entry and answers the provider while every later one is refused with `That request was already answered.` - which is why both now return an `AgentPromptResult` instead of void. The loser does not resolve its own card either: retirement always comes from the session's `approval_resolved`/`decision_resolved` event, the same source the winner sees, so no client can retire a request the agent is still waiting on. Structured answers are bounded by the shared contract (`decisionContentProblem`, `REMOTE_CHAT_ANSWER_*` in `remote-chat.ts`) and validated strictly inbound - a value outside `AgentDecisionValue` is dropped rather than guessed at, because it ends up inside an ACP elicitation response - and the phone's form rules (mutual exclusion of a chosen option and its "Other" field, what counts as answered, when submission is gated) are the pure `mobile/src/decision-answers.ts`. The list side of the same condition reads off the attention model rather than the status, since a parked turn still reports itself as working: `chatNeedsApproval` badges `attention === 'approval'` distinctly from ordinary unread, and `pendingRequestFrom` in `chat-view.ts` is the phone's one reading of "something is pending" - the card, the hidden composer and the "Needs you" pill all derive from it. A tool permission and a structured question set are deliberately _one_ attention condition (kind `approval`, keyed on the request id, raised and retired by the same effect in `ChatNode.tsx` and folded into `sidebarStatus` alike): both are the agent waiting on an answer, and a chat stalled on either has to be findable from a list. Spawning is the one remote operation that is not a session operation at all, and it is the only `POST` on this surface (`POST /api/chats`, contract in `src/shared/remote-spawn.ts`): the canvas owns node identity, geometry, working-directory resolution and launch mode, so main never mints a node - `createRemoteChatSpawner` (`src/main/remote/chat-spawn.ts`) asks the newest live window to run `addSessionNode`, the canvas's own path, which is what makes a phone-spawned node indistinguishable from a right-clicked one (worktree spawning is deliberately not offered). The verdict is never optimistic, because the phone navigates on it: `useRemoteAccess` answers only once the new node's status settles by `spawnSettlement` - `starting` is pending, `exited`/`dormant` are the phantom-chat failures, everything else means the session exists - and every way a desktop can fail to answer (no window, a window closed mid-spawn, a renderer that never replies) is its own refusal rather than a request left open. The verdict also waits on the projection: a chat socket only admits ids the published projection lists, so the hook answers a started spawn only once the host has been handed a projection carrying it - answering sooner would hand the phone an id its very next request would be refused for. `cascadedNodePosition` in `canvas-workspace.ts` is why two spawns do not land on identical coordinates; the phone's form rules are the pure `mobile/src/new-chat.ts`, refusing in the same words `remoteChatSpawnProblem` would. One phone drives several hosts, so the unit every screen is parameterized by is the saved host, not a token. `mobile/src/hosts.ts` owns the list, and two rules are load-bearing: an **origin identifies a host** (pairing one already saved re-pairs that entry and keeps the id its retained drafts are keyed on - so normalize a typed origin _before_ asking the host, since the field accepts a bare authority and a pasted deep link), and a token is **per host** (`revokedHostToken` drops exactly one into re-pairing; a `401` seen anywhere records it on the list, so a background host cannot linger holding a dead token). `host-status.ts` owns per-host reachability plus the retry schedule, and only the probe schedule's own outcomes may pace it - `notedHostOutcome` exists because the chat list's 3s poll would otherwise pin the backoff at its ceiling. `use-host-directory.ts` persists every mutation as it applies it and runs one timer chain per host; `App.tsx` keys every screen on the host id so switching tears the previous host's socket and poll down by remount, and puts the host switcher _ahead_ of the re-pair screen so a revoked token cannot trap the reader. Requests are addressed to a host explicitly (`hostApiUrl`/`hostSocketUrl`) because a relative path would always ask whoever served the page. Cross-origin is CORS rather than per-host bookmarks, argued in the plan doc; in code, `REMOTE_CORS_HEADERS` covers every API reply _including the `401`_ (without it a browser hands the client an opaque network error and a revoked token reads as an outage), the static bundle is served without them, an `OPTIONS` preflight is unauthenticated by necessity, and `*` is safe only because there is no ambient authority to grant - no cookies, no session, `Access-Control-Allow-Credentials` deliberately absent. WebSockets are not CORS-gated, but a browser does refuse `ws:` from an HTTPS page, which `hostBlockedByPageScheme` names rather than letting it read as an offline host. See `tests/remote-access.test.ts`, `tests/remote-server.test.ts`, `tests/remote-spawn.test.ts`, `tests/remote-chat-spawn.test.ts`, `tests/mobile-chat-connection.test.ts`, `tests/mobile-chat-view.test.ts`, `tests/mobile-decision-answers.test.ts`, `tests/mobile-new-chat.test.ts`, `tests/mobile-new-chat.dom.test.tsx`, `tests/mobile-hosts.test.ts`, `tests/mobile-host-status.test.ts`, `tests/mobile-hosts.dom.test.tsx`, `tests/acp-session-manager-broker.test.ts`, `tests/mobile-chat-answers.dom.test.tsx` and `tests/remote-access.dom.test.tsx`.

- The phone client installs itself, and installability is a property of the _origin_ rather than of the client: a service worker demands a secure context, Toucan deliberately owns no certificates, and `tailscale serve` in front of the plain-HTTP listener is the whole HTTPS story - the user-facing walkthrough, security model included, is `docs/mobile-companion-setup.md`. So "not installable" is the ordinary state and not a fault: `mobile/src/install-support.ts` skips with a named reason (`insecure-context` outranks `unsupported`, because an insecure context is _why_ a browser withholds the API, and the wrong one would misdiagnose the fix) and never rejects, so nothing on the loading path depends on a worker existing - while a genuine registration _failure_ is logged, since a failure and a skip send a reader to two different fixes. What the worker may cache is `mobile/src/service-worker-policy.ts` and nowhere else: the shell network-first, Vite's content-hashed `/assets/` cache-first (sound only because the URL changes whenever the bytes do), and pass-through for `/api/`, every non-`GET` and every _other_ origin - one phone drives several hosts, and a cached transcript, chat list or pairing verdict would be a stale workspace presented as live. `mobile/src/sw.ts` is a second, deliberately **unhashed** Vite entry (`sw.js`), because a worker is identified by its URL and a fingerprinted one would register as a brand new worker every build; it declares the handful of worker globals it uses locally rather than pulling in TypeScript's `WebWorker` lib, which redeclares half of `DOM` and so cannot share a program with the rest of `mobile/`. Its one cache is wiped of every other name on activate, so anything a later ticket caches separately has to be named there too. Manifest and icons are static files in `mobile/public/` regenerated by `npm run icon:mobile`, which reads the background colour off the manifest (its one authority) and rasterises the same logo the desktop icon comes from through the shared `scripts/rasterise-logo.mjs`. `tests/mobile-pwa-assets.test.ts` compares every declared `sizes` against the PNG's own IHDR, because Chrome withholds the install prompt _silently_ when they disagree. See also `tests/mobile-install-support.test.ts` and `tests/mobile-service-worker.test.ts`.

- The project sidebar has no `order` field and never will: array order _is_ display order. `projects` stays the single ordered list the remote projection maps, and `WorkspaceState.projectGroups` (optional, added without a version bump, like `attention` and `brainDumpPanel`) orders the groups; the sidebar renders groups first, each followed by the members of `projects` carrying its `groupId`, then the ungrouped ones. Groups are a **desktop-sidebar** affordance - they never reach the canvas, `RemoteProjectSummary`, or `mobile/`. All of the "where does this row land" maths lives in `src/renderer/src/project-order.ts` (no React), and a drag commits on `pointerup` only, because every write to `projects` re-serialises the whole workspace. Two load-time rules make an edited snapshot safe: a `groupId` naming no group is dropped and duplicate group ids are deduped in `parseWorkspaceState`, and a `color` failing `isProjectColor` (`src/shared/project-colors.ts`, the one home of the palette) is _substituted_ from the palette rather than refusing the snapshot - while `isWorkspaceState`, which is also the write-time guard, refuses to store anything but a lowercase `#rrggbb`. A colour is user-changeable now but still denormalised onto node data as `projectColor` at node creation, so `setProjectColor` in `App.tsx` must fan the new colour out across every chat/terminal/worktree node of that project in the same update or the canvas keeps the old tint until the next restore. See `tests/project-order.test.ts` and `tests/project-panel.dom.test.tsx`.

- Work is tracked as GitHub issues on this repo (`gh issue list`). `ready-for-agent` marks a ticket an agent may pick up now; `blocked` plus the issue body's "Blocked by" section gates a ticket on other issues; `backlog` defers it; `frontier-model` flags an architecture-sensitive ticket that should be implemented with the strongest available model rather than the default. When a ticket lands, flip any ticket it was the last blocker for from `blocked` to `ready-for-agent`. Feature plans that spawned a ticket set live under `docs/plans/` and each issue links its plan.

- Every commit message subject follows `type(affected-feature): ticket-number commit-message` - for example `feat(agent): 127 fan agent events out through a main-process broker`. `type` is a conventional-commit type (`feat`, `fix`, `chore`, `refactor`, `docs`, `test`, `build`, `ci`, `perf`), `affected-feature` names the area touched (`agent`, `mobile`, `worktree`, `remote`, ...), and `ticket-number` is the bare GitHub issue number the work belongs to - no `#`, which git would strip as a comment in an editor-composed message. When no issue covers the work, drop the number and keep the rest of the shape. Keep the message itself imperative, lowercase, no trailing period.
- Dictation is English-only on the desktop and says so in its label; the phone prefers its browser's own recognizer and only otherwise posts raw 16 kHz PCM to `POST /api/transcribe`, transcribed in main by the same prepared model files. `src/shared/remote-voice.ts` is the one place the wire shape and the model directory name live, so `scripts/prepare-voice-model.mjs` must fetch the same architecture the renderer and main load. `src/main/remote/voice-engine.ts` is kept out of the test compile because the Moonshine package is ESM-only; the policy around it is tested through an injected engine. Measure accuracy with `npm run voice:wer -- <dir>` on the user's own recordings before changing models. See `docs/voice-input.md`.
